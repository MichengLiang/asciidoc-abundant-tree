在 AsciiDoc 中，自定义宏（Custom Macros）是其极其强大的扩展机制之一。当内置语法无法满足特定需求（例如嵌入特定平台的视频、引用内部的 Jira 编号、或者生成自定义的 UI 组件）时，你可以通过 Asciidoctor 的 **扩展 API (Extensions API)** 来定义自己的宏语法。

AsciiDoc 的自定义宏在 `.adoc` 源码文件中表现为一种非常结构化且易读的格式，主要分为行内宏（Inline Macros）**和**块级宏（Block Macros）两种形态。

---

### 一、 自定义宏的语法外观

无论是哪种宏，AsciiDoc 都强制采用统一的语义结构：`宏名称` + `冒号` + `目标(Target)` + `方括号包裹的属性(Attributes)`。

#### 1. 行内宏 (Inline Macros)

行内宏用于段落文本内部，通常用于替换词汇、添加特定链接或注入行内样式。
**语法规则：** `名称:目标[属性]` （单冒号）

**代码示例：**

```asciidoc
你好，请参考 issue 追踪器中的 bug:12345[status=resolved] 了解修复详情。

你可以通过 user:linus_torvalds[role="admin", style="bold"] 联系管理员。

```

#### 2. 块级宏 (Block Macros)

块级宏独占一行，通常用于插入独立的内容块，如视频、图表、外部代码段或自定义的警告框。
**语法规则：** `名称::目标[属性]` （双冒号）

**代码示例：**

```asciidoc
= 系统架构文档

以下是核心模块的依赖关系图：

plantuml::architecture/core_modules.puml[format=svg, width=100%]

.相关推文
tweet::1234567890987654321[theme="dark", align="center"]

```

---

### 二、 宏的组成部分深度解析

* **名称 (Name/Context)：** 宏的唯一标识符。在编写扩展解析器时，系统会根据这个名字来拦截对应的语法。通常由小写字母组成。
* **冒号 (`:` 或 `::`)：** 严格区分了该宏在文档 AST（抽象语法树）中是被作为 `inline` 节点还是 `block` 节点处理。
* **目标 (Target)：** 紧跟在冒号后面的主要数据（例如 ID、URL、文件路径）。如果不需要目标，可以留空，但冒号和方括号必须保留（例如 `clear::[]`）。
* **属性 (Attributes)：** 写在 `[]` 中。支持位置参数（如 `[svg, 100%]`）和键值对参数（如 `[format=svg, width=100%]`）。

---

### 三、 底层实现机制 (Asciidoctor Extensions API)

自定义宏不仅仅是写在文本里的占位符，它们需要一个“后端的处理器”来将其转换为最终的 HTML 或 PDF 输出。这通常通过 Ruby 或 JavaScript (Asciidoctor.js) 编写扩展来实现。

以下是一个使用 Asciidoctor Ruby API 编写**自定义块级宏**的深度示例，展示了宏是如何被引擎解析和渲染的。

#### 场景：创建一个嵌入 GitHub Gist 的块级宏

**1. AsciiDoc 源文件 (`example.adoc`):**

```asciidoc
这里是一段复杂的算法实现：

gist::1234567[file="algorithm.rb"]

```

**2. 处理器代码 (Ruby):**
我们需要注册一个 `BlockMacroProcessor` 来拦截 `gist` 这个名称。

```ruby
require 'asciidoctor'
require 'asciidoctor/extensions'

include Asciidoctor

# 定义扩展类
class GistBlockMacro < Extensions::BlockMacroProcessor
  use_dsl
  
  # 绑定宏名称为 gist
  named :gist

  # 处理逻辑：parent 是父节点，target 是宏的目标(如 1234567)，attributes 是属性哈希
  def process parent, target, attributes
    # 提取属性（如果没传 file 属性，则为空）
    file_param = attributes.key?('file') ? "?file=#{attributes['file']}" : ''
    
    # 构建最终的 HTML 内容
    html = %(<div class="gist-wrapper">
      <script src="https://gist.github.com/#{target}.js#{file_param}"></script>
    </div>)

    # 将生成的 HTML 作为一个 pass（透传）块插入到文档结构树中
    create_pass_block parent, html, attributes, subs: nil
  end
end

# 注册扩展
Extensions.register do
  block_macro GistBlockMacro
end

# 编译文档
Asciidoctor.convert_file 'example.adoc', safe: :safe

```

#### 工作原理拆解：

1. 引擎在解析 `example.adoc` 时，遇到了 `gist::1234567[file="algorithm.rb"]`。
2. 引擎发现 `gist` 已经注册在 `BlockMacroProcessor` 中。
3. 引擎调用 `process` 方法，传入：
* `target` = `"1234567"`
* `attributes` = `{"file" => "algorithm.rb"}`


4. 处理器生成了一段 `<script>` 标签构成的 HTML。
5. 处理器将这段 HTML 组装成一个新的文档节点（Block），替换掉了原来的宏语法，最终输出到 HTML 文件中。

### 四、 典型的应用场景

在大型文档工程或开发者门户中，自定义宏极大地提升了文档的可维护性：

1. **统一术语引用：** `term:k8s[tooltip=true]` 可以自动生成带悬浮提示的术语标准缩写。
2. **API 文档集成：** `openapi::swagger.json[endpoint="/users", method="GET"]` 可以在构建时动态去拉取 API 接口数据并渲染成表格。
3. **UI 组件库调用：** `alert::warning[title="注意"]` 被处理器拦截后，可以生成复杂的、符合企业 UI 规范的 HTML/CSS 警告框代码，而不需要作者手写大量冗长的语法。

本项目还实现了 project-specific 行内宏 `hmeta:<field>[...]`，用于在正文句子中放置面向读者显示的标题元数据标记。它的完整解析和 RDF 投影契约以对应设计文档和实现测试为准。
