结论先说清楚：你的判断是对的。当前 TTL 里有标题、有 `containsDirectly`、有 `previousSibling`、有 source file raw，但是下游想“直接按书籍阅读顺序重建大纲”并不好做，而且在 book-entry 多文件场景里现有 RDF 边本身还存在顺序/层级不可靠的问题。更稳的做法是在 RDF 1.2 投影里新增一份“整本书已序列化的大纲 literal”，让下游直接读取这个 literal，不再要求下游从源文件 raw、标题节点、兄弟边、包含边反推书籍结构。

## 一、当前生成链路实际是怎样的

项目入口在 `src/parser.ts`。如果 CLI 使用：

```bash
pnpm exec tsx src/cli.ts <book.adoc> --mode book-entry --document-root <root> --format rdf12
```

那么代码走的是 `parseAbundantTree({ mode: "book-entry" })`。这个模式不会直接让 RDF 层逐个读 include；它先调用 `src/book-entry/logical-source-builder.ts` 的 `buildLogicalSource`。这个 builder 会递归读取 entry 文件里的 `include::...[]`，把普通行 append 到 `logicalLines`，把 include 目标文件的内容展开到逻辑文本里，并且同时保存每一行逻辑行对应的原始文件路径与原始行号。最后得到：

- `logicalText`：已展开 include 的整本文本。
- `lineOrigins`：逻辑行到源文件行的映射。
- `sourceFiles`：每个参与文件的 `relativePath` 和完整 `raw`。

然后 `parser.ts` 把 `logicalText` 交给 `adapter.loadSource(logicalSource.logicalText)`，再由 `src/parser-core.ts` 的 `parseAsciidoctorDocument` 生成 `AbundantDocument`。这个 `AbundantDocument` 里面有：

- `title`：文档标题，也就是书名。
- `children`：Asciidoctor block 树投影后的结构节点。
- `sourceFiles`：全部原始源文件 raw。
- `targets` / `xrefOccurrences` / `anchorOccurrences` 等。

也就是说，当前 JSON 模型层其实已经有“按书籍阅读顺序组织好的树”。真正的问题出在 RDF 层：`src/rdf12-projection/structure-projector.ts` 并不是按 `document.children` 的树顺序直接输出一个线性大纲，而是先 `collectSections(document.children)` 打平成 section 列表，然后 `projectHeadingStructureEdges` 再按 `entry.startLine` 排序并用标题 level 栈重建 containment/sibling 边。这个做法对单文件比较自然，但对 book-entry 多文件会出问题，因为每个 include 文件的源行号都是从 1 开始，多个章节都可能 `startLine = 1` 或 `headingLine = 1/2`。于是 RDF 层失去了逻辑展开顺序。

## 二、关于 HTML 解析：确实用了，但现在不是用来拿整书大纲

你提到“这里应该用到了 HTML 解析，现在解析是为了拿链接”。我查到 `src/asciidoctor-adapter.ts` 确实 import 了 `parse5`：

```ts
import { type DefaultTreeAdapterMap, parseFragment } from "parse5";
```

但它现在只做两类事情：

1. `extractAnchorBindings(html)`：解析一小段 HTML fragment，遍历 `<a>` 元素，拿 `href`、`id`、text。
2. `resolveXrefBinding(...)`：用 Asciidoctor runtime 创建 inline anchor，然后 convert 成 HTML，再用 `parse5` 解析 anchor，得到官方解析后的 xref href/reftext/resolvedId。

也就是说，当前 parse5 没有在解析完整 HTML 文档，也没有在解析 HTML TOC。它只是把 Asciidoctor 转出来的一小段 inline anchor HTML 当作官方 xref 绑定证据。

理论上可以让 Asciidoctor 转完整 HTML，然后用 parse5 去抓 TOC 或 heading DOM。但是我不建议这样做，至少不建议作为这个需求的主实现。原因是：

- 现在 `AbundantDocument.children` 已经是 Asciidoctor block tree 的结构投影，它比 HTML TOC 更接近项目内部模型，不需要再经过 HTML 输出格式。
- HTML TOC 受 backend、doctype、toc 配置、主题和 converter 行为影响；把“书籍大纲 projection”建立在 HTML 输出上，会引入不必要的格式耦合。
- parse5 当前只解析 fragment，没有完整 document converter 链路；为了拿大纲去新增完整 HTML 解析链路，改动更大，风险更高。
- 你要的是“原始字符串、按 AsciiDoc 标题语法表达、下游直接消费”，从模型层直接序列化更稳。

所以我的建议是：不要为了这个需求扩展 HTML 解析；直接从 `AbundantDocument.title + AbundantDocument.children` 生成一个 AsciiDoc heading-lines string，然后把它作为 RDF literal 投影出来。

## 四、当前 TTL 为什么不够用，而且在大样例上确实错了

我也运行了 RDF 输出：

```bash
pnpm exec tsx src/cli.ts ... --format rdf12 > /tmp/aat-structured-writing.ttl
```

当前 TTL 里每个 heading 都有类似这些事实：

- `a aat:Heading`
- `aat:headline "..."`
- `aat:headingLevel ...`
- `aat:relativePath "..."`
- `aat:startLine ...`
- `aat:endLine ...`
- `aat:raw """..."""`
- `aat:containsDirectly ...`
- `aat:previousSibling ...`

表面上看这些足够重建树，但实际有两个硬问题。

第一个问题是 RDF 对象列表本身没有语义顺序。比如一个 subject 上有多个 `aat:containsDirectly` object，在 Turtle 里即使写成逗号列表，RDF 语义也不是 ordered list。下游不能把 Turtle 文本里的对象排列当成稳定顺序。除非使用 `rdf:List`、显式 `aat:sequence`、`aat:nextSibling`/`previousSibling` 并严格遍历，否则没有直接顺序。

第二个问题更严重：当前 `previousSibling` 和 `containsDirectly` 的生成算法在 book-entry 多文件场景下不可靠。`structure-projector.ts` 里 `projectHeadingStructureEdges` 先把 node index entries 做：

```ts
.toSorted((left, right) => left.startLine - right.startLine)
```

但 book-entry 下 `startLine` 是原始 source file 内的行号。frontmatter、chapter、backmatter 文件都可能从第 1 行开始。这样排序不是“逻辑展开顺序”，而是“各自文件内行号排序”。在我生成的大样例 TTL 里，根标题的 `aat:containsDirectly` 直接包含了大量 level 1 heading 和三个 part；而且 `= 从源文档看结构` 的 `aat:previousSibling` 指向了 `索引`。这已经不是只是不方便，而是对“书籍顺序”来说明显错误：第一部不应该排在索引后面。

小样例 `samples/book-entry-demo` 也能看到风险。当前 JSON 递归大纲是：

```adoc
= Book Entry Demo
== Overview
== Operations
=== Checklist
```

这份结构从 `document.children` 很容易得到；但 TTL 里 heading 资源 ID 和 sibling/containment 仍依赖跨文件源行坐标。简单样例刚好没有暴露出第一部跑到索引后面那种明显错误，但它同样不是一个“下游直接消费的大纲”。

## 五、现有 sourceFile raw 的定位是正确的，但它不是大纲

`src/rdf12-projection/source-file-projector.ts` 会把 `document.sourceFiles` 投影为：

```ttl
<#source> aat:sourceFile <#source-file-...> .
<#source-file-...> a aat:SourceFile ;
  aat:relativePath "..." ;
  aat:raw """...""" .
```

`book-entry-demo/tmp/out.ttl` 里也确实能看到每个原始文件完整 raw。这符合“这里存储的是原始文件，不展开”的要求。这个设计不要改。它的职责是 provenance/source retention，不应该被改成 logical expanded source，也不应该让下游从这里重新 parse include。你现在要的是另一个层面的东西：在投影结果里额外放一个“已计算完成的书籍大纲字符串”。

## 六、推荐新增的数据形态

我建议新增一个单独 literal，挂在 projection entity 上：

```ttl
<#projection> aat:outlineRaw """= 结构化书写约定标本
== 摘要
== 版本说明
== 献辞
== 前言
== 致谢
= 从源文档看结构
== 源文本与投影
== 标题与引用
== 源文件编排号
= 给标题和引用加意图
== role 身份
== rel 关系谓词
= 字段、索引与术语
== 附加字段
== 索引词与术语表
== 附录 A：结构化写法速查
== 术语表
== 参考坐标
== 索引
""" .
```

谓词名字可以再斟酌，我倾向于以下之一：

- `aat:outlineRaw`：短，和现有 `aat:raw` 风格一致，表示这是大纲的 raw textual projection。
- `aat:bookOutlineRaw`：更明确只服务 book-entry/book outline。
- `aat:serializedOutline`：强调这是序列化结果，但不说明语法。

如果只选一个，我建议 `aat:outlineRaw` 或 `aat:bookOutlineRaw`。考虑下游工具链直觉，我更偏向 `aat:bookOutlineRaw`，因为它说明这是整本书的大纲，不是某个 heading 的 raw。

subject 我建议挂在 `#projection` 上，而不是某个 heading 上。原因是这份字符串是“投影产物”，不是某个源文件 raw，也不是某个 heading 自身属性。挂在 `#projection`，下游拿到 `aat:HeadingProjection` 后可以直接查：

```sparql
?projection a aat:HeadingProjection ;
            aat:bookOutlineRaw ?outline .
```

也可以考虑同时挂在 `#source` 上，但这会让它看起来像 source document 的原生属性。为了语义干净，先挂 projection 足够。

## 七、实现位置建议

我建议加一个很小的模块，例如：

```text
src/rdf12-projection/book-outline.ts
```

职责只做两件事：

1. 从 `AbundantDocument` 生成 outline string。
2. 把这个 string 作为 RDF triple 加进 graph。

伪代码大概是：

```ts
export function serializeBookOutline(document: AbundantDocument): string | undefined {
  const lines: string[] = [];

  if (document.title?.text) {
    lines.push(`= ${document.title.text}`);
  }

  appendSections(lines, document.children);

  if (lines.length === 0) {
    return undefined;
  }

  return `${lines.join("\n")}\n`;
}

function appendSections(lines: string[], nodes: readonly AbundantNode[] | undefined): void {
  for (const node of nodes ?? []) {
    if (node.kind !== "section") continue;
    lines.push(`${"=".repeat(node.level + 1)} ${node.title}`);
    appendSections(lines, node.children);
  }
}
```

然后在 `src/rdf12-projection/projector.ts` 里，在 `addProvenanceTriples` 或 `projectStructureResources` 之后调用：

```ts
projectBookOutline({
  graph,
  projectionIri,
  document,
});
```

`projectBookOutline` 内部添加：

```ts
graph.add(
  rdf12Triple(
    projectionIri,
    iriTerm(`${namespaces.aat}bookOutlineRaw`),
    stringLiteral(outline),
  ),
);
```

这一路径改动很小，不会改变现有 heading、xref、payload、sourceFile 的投影逻辑，也不会影响现有 source raw 保留策略。

## 八、Turtle serializer 需要同步改一个细节

当前 `src/rdf12-projection/turtle-serializer.ts` 有一个可读性后处理：`formatReadableRawLiterals`。它只识别谓词 `aat:raw`，把包含换行的普通 quoted string 改成三引号长字符串。新增 `aat:bookOutlineRaw` 后，如果不改这里，N3 writer 仍然能输出合法 Turtle，但大纲 literal 可能以 `\n` escape 的形式出现，不符合你想要“直接看起来就是一份 adoc 大纲”的体验。

所以应该把这个函数泛化一下，不只识别 `aat:raw`，也识别 `aat:bookOutlineRaw`。例如把 `startsRawPredicate` 改成 `startsReadableLongLiteralPredicate`，允许：

- `aat:raw`
- `aat:bookOutlineRaw`

这样 TTL 里会自然出现：

```ttl
aat:bookOutlineRaw """= Book Entry Demo
== Overview
== Operations
=== Checklist
""" .
```

这符合你说的“直接存一份序列化好的，下游直接拿”。

## 九、是否需要记录 part / preface / glossary / index 的结构关系

如果目标只是下游重建大纲字符串，那么不必先建 `BookPart`、`Preface`、`Glossary`、`Index` 这些 RDF class。大纲 literal 里已经按顺序包含标题文本和层级。

但这次调查也确认：`SectionNode.metadata` 里能看到特殊 section style。大样例 JSON 里这些 metadata 都存在：

- `[abstract]` -> `attributes.style = "abstract"`
- `[colophon]` -> `"colophon"`
- `[dedication]` -> `"dedication"`
- `[preface]` -> `"preface"`
- `[acknowledgments]` -> `"acknowledgments"`
- `[appendix]` -> `"appendix"`
- `[glossary]` -> `"glossary"`
- `[bibliography]` -> `"bibliography"`
- `[index]` -> `"index"`

所以如果未来要做更强的结构语义，也有数据来源。但这不是这次需求的最小必要条件。最小闭环是：新增 `bookOutlineRaw` 字符串 literal。它不阻止以后再加 `aat:sectionStyle`、`aat:bookRole` 或 ordered RDF list。

第四类：Turtle 可读性测试。确保 `aat:bookOutlineRaw` 在 TTL 里是三引号长字符串，而不是一行带 `\n` escape 的字符串。

第五类：JSON-LD 测试。JSON-LD serializer 是 triple 列表，理论上不用特别改，但应该断言能看到 predicate `aat:bookOutlineRaw` 和 literal value。

## 十一、现有 `containsDirectly` / `previousSibling` 要不要修

这和“新增大纲 literal”是两个问题。

就你这次的需求来说，新增 `bookOutlineRaw` 可以独立解决下游直接消费大纲的问题，不必同时修所有结构边。这样改动范围小，风险低。

但调查中确实发现 `projectHeadingStructureEdges` 在 book-entry 多文件书上按 `startLine` 排序会错。这个问题后续应该单独修。合理修法不是让下游依赖 source line，而是让 node index 或 structure projector 保留“document traversal order”。例如在 `projectStructureResources` 遍历 `document.children` 时给每个 heading entry 写入一个 `documentOrder` 或内部 order 字段，然后 `projectHeadingStructureEdges` 按这个 order 处理。更理想的是直接递归 `document.children` 投影 containment，而不是 flatten 后按行号重建。但这是另一个行为变更，会影响现有 RDF query contracts，需要单独测试。

因此我建议分两步：

1. 先加 `aat:bookOutlineRaw`，满足下游直接拿有序大纲的需求。
2. 再单独修 book-entry 下 `containsDirectly`/`previousSibling` 的顺序和层级语义，避免 RDF 结构边在多文件书上误导消费者。

## 十二、最终建议

最小可行实现是：

- 新增 `serializeBookOutline(document)`：从 `document.title` 和 `document.children` 递归生成 AsciiDoc heading-lines string。
- 新增 RDF triple：`<#projection> aat:bookOutlineRaw """..."""`。
- 修改 Turtle serializer，让 `aat:bookOutlineRaw` 多行 literal 使用三引号输出。
- 增加 book-entry 多文件测试，尤其覆盖多个 include 文件标题都在第 1 行的情况。

这个方案满足你提出的几个约束：

- 不改变 sourceFile raw 的含义，原始文件仍然原样保存。
- 不要求下游展开 include。
- 不要求下游从 RDF 无序对象列表和 sibling 边重建顺序。
- 使用 AsciiDoc 自己的标题语法表达大纲。
- 可以保留 part、frontmatter、backmatter、index 的阅读位置顺序。
- 实现点贴近现有 RDF projector，不需要引入完整 HTML parse 链路。

我认为下一步可以直接实现这个最小方案。实现时我会避免碰 source-file projector，只在 RDF projection 新增一个 outline projector，并补对应测试。

# TTL 大纲与 heading 结构边：根治方案调查

我继续查了 `node-index`、`structure-projector`、`xref-projector`、项目自带的 RDF heading projection 规约书和 book-entry logical document 规约书。现在可以更明确地回答你的问题：只加一份 `bookOutlineRaw` 字符串确实能让下游短期好用，但它不是理想模型；真正应该从 heading 结构边和顺序模型本身治理。当前问题本质上不是“TTL 没有按顺序打印”，而是投影器把两种坐标混用了：

- 结构/阅读顺序应该来自 logical document，也就是 Asciidoctor 解析展开后的 section tree。
- 回源坐标和 raw slice 应该来自 origin source file，也就是 `relativePath + startLine/endLine/raw`。

当前 `structure-projector.ts` 在生成 `aat:containsDirectly` 和 `aat:previousSibling` 时，把 heading resource 的 origin `startLine` 当成了结构排序依据。这在 single-file 模式下刚好成立，但在 book-entry 多文件模式下必然错，因为每个 include 文件都有自己的第 1 行、第 2 行。这个不是小输出问题，是模型生成算法把“回源坐标”误当成了“文档顺序坐标”。

## 一、我现在怎么判断这不是“正常限制”，而是实现错误

项目自己的规约书已经把这个说清楚了。

`docs/bookshelf/books/06-rdf12-line-projection/chapters/04-structure-edges.adoc` 里写了：

- `aat:containsDirectly` 表达父标题到直接子标题的关系。
- `aat:previousSibling` 表达同一父标题下的前一个兄弟标题。
- `aat:previousSibling` 不跨父标题。
- line span 负责回源，`previousSibling` 负责结构顺序。

`docs/bookshelf/books/10-book-entry-source-mapped-logical-document/chapters/08-source-coordinate-recovery.adoc` 又写了一个关键规则：

- Heading raw 必须从 origin source file line table 恢复。
- Heading raw 终点按 origin source file 内的 heading slice 规则确定。
- Logical document 只提供结构关系，不提供 raw slice source。

这两本规约放在一起，含义非常明确：book-entry 下必须把“结构关系”和“raw 回源”分开处理。结构关系来自 logical document / official section tree；raw 和 source coordinate 来自 line origin 映射后的 origin source file。当前 `projectHeadingStructureEdges` 按 `startLine` 排序，就是把 raw 回源坐标拿来做结构顺序，因此违反了这个分层。

所以我同意你的判断：这应该视为 projection algorithm bug，而不只是下游消费不方便。

## 四、关于“TTL 是纯文本，能不能靠从上往下排”

这里要分两层说。

作为人类阅读，当然可以把 TTL 打印成从上到下，甚至可以让 heading subject 出现顺序符合书籍顺序。这对 debug 和人工检查有价值。

但作为下游工具链的机器契约，不能依赖 Turtle 文本行顺序。原因有三个。

第一，RDF graph 本身没有 triple 顺序。Turtle 是 RDF graph 的一种具体语法，不是 ordered document model。多个 triple 的排列顺序不构成 RDF 语义。任何 RDF parser 读进去之后都可以重新排序、去重、按 subject/predicate/object hash 存储。

第二，当前项目自己的 `Rdf12Graph.toArray()` 就已经按 triple key 字符串排序，不保留 projector 写入顺序：

```ts
return Array.from(this.#triplesByKey.entries())
    .sort(([leftKey], [rightKey]) => compareCodeUnits(leftKey, rightKey))
    .map(([, triple]) => triple);
```

所以即使我们按书籍顺序 `graph.add(...)`，最终 TTL 也会按 key 排序。你在大样例里看到 `heading-l1-o10` 出现在 `heading-l1-o1` 前面，就是字符串排序副作用。只靠“写入顺序”在当前 serializer 下根本不会生效。

第三，即使我们专门改 Turtle writer，让它按 `documentOrder` 打印 subject，消费者如果用 RDF 库读取 TTL，也仍然不会自动保留这个 textual order。除非下游直接把 TTL 当文本解析，那就绕开了 RDF 模型，后面会很脆。

所以理想设计不是“让 TTL 从上到下排好就完事”，而是：

- RDF 图里显式建模顺序，例如 `aat:previousSibling`、`aat:documentOrder`。
- Turtle 输出可以按这个顺序排版，但这只是可读性，不是唯一语义来源。
- 如果下游想要最简单的文本大纲，再额外给 `aat:bookOutlineRaw` 作为 convenience literal。

## 五、理想模型应该是什么样

我现在认为理想状态应该分三层。

### 第一层：标题节点仍然是资源节点

每个标题继续是 `aat:Heading`。保留现有事实：

```ttl
:heading-x a aat:Heading ;
  aat:headline "..." ;
  aat:headingLevel 1 ;
  aat:relativePath "..." ;
  aat:startLine 1 ;
  aat:endLine 7 ;
  aat:raw """...""" .
```

这些字段里 `relativePath/startLine/endLine/raw` 继续描述 origin source file，不要改成 logical line。这个是 book-entry 回源契约，不能破坏。

### 第二层：结构关系从 `AbundantDocument.children` 生成

`aat:containsDirectly` 和 `aat:previousSibling` 应该来自 `document.children` 这棵树，而不是从 line span 排序反推。也就是说：

- `document.title` 可以作为 root heading。
- `document.children` 里的 section 是 root 的直接子标题。
- section.children 里的 section 是该 section 的直接子标题。
- 同一个 `children` 数组内的相邻 section 生成 `previousSibling`。
- paragraph/listing/table 等非 heading 不参与 structure edge。

对于大样例，正确的顶层 sibling 链应该是：

```text
摘要
版本说明 previousSibling 摘要
献辞 previousSibling 版本说明
前言 previousSibling 献辞
致谢 previousSibling 前言
从源文档看结构 previousSibling 致谢
给标题和引用加意图 previousSibling 从源文档看结构
字段、索引与术语 previousSibling 给标题和引用加意图
附录 A：结构化写法速查 previousSibling 字段、索引与术语
术语表 previousSibling 附录 A：结构化写法速查
参考坐标 previousSibling 术语表
索引 previousSibling 参考坐标
```

而 `从源文档看结构` 应该 `containsDirectly`：

```text
源文本与投影
标题与引用
源文件编排号
```

`给标题和引用加意图` 应该 `containsDirectly`：

```text
role 身份
rel 关系谓词
```

`字段、索引与术语` 应该 `containsDirectly`：

```text
附加字段
索引词与术语表
```

这就是书籍结构，不需要看 origin 行号。

### 第三层：增加显式全书顺序号，方便下游直接 ORDER BY

只修 `previousSibling` 已经符合项目规约，但对下游来说还是要从 root 出发递归查 `containsDirectly`，再在每组 sibling 里找链头并按 `previousSibling` 排列。这能做，但不够轻松。

因此我建议额外给每个 heading 写一个全书 pre-order 序号，例如：

```ttl
:heading-title aat:documentOrder 0 .
:heading-abstract aat:documentOrder 1 .
:heading-colophon aat:documentOrder 2 .
:heading-dedication aat:documentOrder 3 .
:heading-preface aat:documentOrder 4 .
...
:heading-index aat:documentOrder 19 .
```

名字可以叫：

- `aat:documentOrder`
- `aat:outlineOrder`
- `aat:bookOrder`

我倾向 `aat:documentOrder`，因为它不是只为 outline 字符串服务，而是表达 heading 在 logical document 的全局 traversal order。

这样下游想拿线性大纲就非常简单：

```sparql
SELECT ?order ?level ?headline WHERE {
  ?heading a aat:Heading ;
           aat:documentOrder ?order ;
           aat:headingLevel ?level ;
           aat:headline ?headline .
}
ORDER BY ?order
```

这比解析 TTL 文本顺序稳，也比从 sibling 链重建简单。`containsDirectly` 保留树结构，`previousSibling` 保留同父顺序，`documentOrder` 保留全局书籍阅读顺序。三个事实互相补充，不冲突。

## 六、那 `bookOutlineRaw` 还要不要加

我现在的判断是：要加，但它应该是 convenience projection，不应该是根部修复的唯一手段。

也就是说，理想方案不是：

```text
结构边先不管，只加一份字符串。
```

理想方案应该是：

```text
先修结构边和顺序模型，再从同一个顺序模型派生 bookOutlineRaw。
```

`bookOutlineRaw` 的价值仍然很明显：有些下游工具不想跑 SPARQL，不想理解 RDF sibling chain，只想拿一段 adoc 大纲给 LLM、编辑器、检索器或导航工具。那它直接读：

```sparql
?projection aat:bookOutlineRaw ?outline .
```

这很合理。但它应该是从正确模型派生出来的缓存/便捷出口，而不是绕过错误结构边的补丁。

## 七、最小根治改法可能比想象中小

好消息是，最小修复不一定要大重构。

当前 `projectStructureResources` 投影 heading 的顺序已经是正确的：

```ts
projectDocumentTitleHeading(context);
for (const section of collectSections(input.document.children)) {
    projectHeading(context, section);
}
projectHeadingStructureEdges(context);
```

`collectSections` 是 DFS pre-order。`nodeIndex.set()` 是 push 到数组。也就是说 `context.nodeIndex.entries()` 已经是：document title、摘要、版本说明、献辞、前言、致谢、第一部、第一部章节、第二部……这样的逻辑文档顺序。

所以第一步根治可以很直接：在 `projectHeadingStructureEdges` 里不要按 `startLine` 排序，而是使用 node index 原始 entry 顺序。

当前：

```ts
const entries = context.nodeIndex
    .entries()
    .toSorted((left, right) => left.startLine - right.startLine);
```

建议改成：

```ts
const entries = context.nodeIndex.entries();
```

或者更明确一点，给 node index entry 增加 `documentOrder` 字段，按 `documentOrder` 排序：

```ts
const entries = context.nodeIndex
    .entries()
    .toSorted((left, right) => left.documentOrder - right.documentOrder);
```

我更建议加 `documentOrder`，因为它可以同时投影到 RDF，并且能让内部意图显性化：这里排序的是 logical document order，不是 source line order。

不过要注意：如果只改这一行，结构边大概率已经能修正；但没有 `documentOrder` 的话，下游仍然不能一条查询得到线性顺序。因此“工程最小修复”和“理想公开模型”还差一个公开顺序谓词。

## 八、实现方案建议

我建议分三步实现，每一步都有可验收产物。

### Step 1：修 `containsDirectly` / `previousSibling`

目标：让结构边从 logical document order 建立。

实现方式：

- 保持 `projectHeading` 继续写 heading resource、raw、source coordinate。
- 修改 `projectHeadingStructureEdges`，不要按 `startLine` 排序。
- 使用 `nodeIndex.entries()` 的 document traversal order。
- 继续用现有 stack 按 heading level 算父子关系。

为什么现有 stack 还可以用？因为 entries 顺序如果是 DFS pre-order，那么 stack 算法是合理的：遇到更深 level 就入栈成为子标题，遇到同级或更浅 level 就 pop 到合适父级。

这一步应该新增一个 book-entry 多文件测试，专门证明：

- 第一部的 previousSibling 是致谢，不是索引。
- 第一部 containsDirectly 它自己的三个 chapter。
- 第二部 previousSibling 是第一部。
- 索引 previousSibling 是参考坐标。
- root 不直接 contains part 内 chapter。

### Step 2：给 heading 节点增加 `aat:documentOrder`

目标：给下游一个不用解析 sibling chain 的全书线性顺序。

实现方式可以是：

- 在 `Rdf12NodeIndexEntry` 增加 `documentOrder: number`。
- `StructureProjectorContext` 增加 `nextDocumentOrder` 或 order allocator。
- `projectDocumentTitleHeading` 给书名 order 0。
- 每次 `projectHeading` 时按 document traversal order 分配递增整数。
- `projectHeading` 写 triple：`aat:documentOrder` xsd integer。

这样下游可以简单 `ORDER BY ?documentOrder`。这比依赖 TTL 行顺序健康很多。

### Step 3：从正确模型派生 `aat:bookOutlineRaw`

目标：给不想理解 RDF 图结构的下游直接读取的 adoc 大纲。

实现方式：

- 新增 `serializeBookOutline(document)` 或从 node index entries 生成。
- 如果从 `document` 生成，保证和 Step 1 使用同一棵 tree。
- 如果从 node index 生成，保证按 `documentOrder` 排序。
- 写到 `<#projection> aat:bookOutlineRaw """..."""`。
- 修改 Turtle readable literal formatter，让 `aat:bookOutlineRaw` 使用三引号多行输出。

大样例输出应该是：

```adoc
= 结构化书写约定标本
== 摘要
== 版本说明
== 献辞
== 前言
== 致谢
= 从源文档看结构
== 源文本与投影
== 标题与引用
== 源文件编排号
= 给标题和引用加意图
== role 身份
== rel 关系谓词
= 字段、索引与术语
== 附加字段
== 索引词与术语表
== 附录 A：结构化写法速查
== 术语表
== 参考坐标
== 索引
```

这里的等号数量应该按全书逻辑层级，而不是各源文件原文层级。因为它是“书的大纲”，不是“每个源文件标题行原样摘录”。

## 九、为什么不建议用 RDF List 作为主方案

也可以用 RDF List：

```ttl
<#projection> aat:outlineHeadings (
  :heading-title
  :heading-abstract
  :heading-colophon
  ...
) .
```

这在 RDF 语义上是 ordered list，理论上很正。但我不建议作为第一选择，原因是：

- Turtle 输出会更啰嗦，解析时要处理 `rdf:first/rest/nil`。
- 现有项目 graph adapter / JSON-LD serializer 没有针对 RDF collection 的专门抽象；N3 writer 可以写，但内部 graph 仍是 triples。
- 下游如果只是想排序，`aat:documentOrder` 更直接。
- `containsDirectly + previousSibling + documentOrder` 已经足够表达树、局部顺序和全局线性顺序。

RDF List 可以作为将来增强，但不是这次根治的最佳切入点。

## 十、是否要改变 heading resource ID

暂时不建议改。

现在 heading local id 形如：

```text
heading-l1-o1
heading-l1-o2
heading-l32-o0
```

其中 `l` 是 startLine，`o` 是同坐标 ordinal。book-entry 下多个文件都有 `startLine=1`，所以 `o1/o2/o3...` 其实已经在用 ordinal 区分。这个 ID 对人类不完美，但贸然改会影响大量测试、xref edge、label catalog 和下游缓存。

更合理的处理是：

- 保持 ID 兼容。
- 新增 `aat:documentOrder` 表达真正顺序。
- 必要时以后再设计更稳定的 resource identity，比如把 source file hash 或 path slug 纳入 local id。但那是另一个破坏性更强的版本变更。

当前问题不需要通过改 ID 解决。

## 十一、现有 xref 绑定有没有一起坏

我查了 `src/rdf12-projection/xref-projector.ts`。它比 structure edge 更谨慎。source heading 查找时会比较 `relativePath`：

```ts
entry.relativePath === occurrence.relativePath &&
entry.sourceStartLine <= occurrence.line &&
occurrence.line <= entry.sourceEndLine
```

这和 book-entry 规约里的“Source Scope 查找必须同时比较 relativePath”一致。所以 xref 绑定没有同样直接使用全书排序。之前已经有提交 `fix: bind rdf12 xref scopes by origin path`，说明这一块已经修过多文件同号行问题。

这意味着我们不应该把整个 RDF 投影都推倒重做。主要根治范围是：

- heading structure edge 生成。
- heading global order 暴露。
- outline literal 从正确顺序派生。

xref projector、source-file projector、payload projector 不需要跟着大改。

## 十二、测试应该怎样设计才算真的证明修好了

我建议新增一个专门的 book-entry RDF structure edge 测试，不要只靠现有 `samples/book-entry-demo`。因为小样例太简单，不足以暴露“索引跑到第一部前面”这种问题。

可以在 `test/book-entry/fixtures` 或 `test/rdf12-projection/fixtures` 新建一个小书：

```adoc
= Test Book
:doctype: book

[preface]
include::frontmatter/preface.adoc[]

= Part One

include::parts/100/010-first.adoc[]
include::parts/100/020-second.adoc[]

= Part Two

include::parts/200/010-third.adoc[]

[index]
include::backmatter/index.adoc[]
```

让每个 include 文件的 heading 都从第 1 行开始。这样如果投影器继续按 origin `startLine` 排序，测试必然失败。

断言应该包括：

- 所有 heading 都有递增 `aat:documentOrder`。
- `ORDER BY documentOrder` 得到 `Test Book, Preface, Part One, First, Second, Part Two, Third, Index`。
- `Part One containsDirectly First/Second`。
- `Part Two containsDirectly Third`。
- root/document title containsDirectly `Preface, Part One, Part Two, Index`。
- `Part One previousSibling Preface`。
- `Part Two previousSibling Part One`。
- `Index previousSibling Part Two`。
- `First` 没有 `previousSibling`。
- `Second previousSibling First`。
- root 不直接 contains `First/Second/Third`。

再加一个 `bookOutlineRaw` 测试，断言 literal 等于：

```adoc
= Test Book
== Preface
= Part One
== First
== Second
= Part Two
== Third
== Index
```

注意这里是否输出 `== Preface` 取决于模型里的 level。如果 preface include 文件写 `== Preface`，输出就是 `== Preface`；如果它写 `= Preface` 但在 book 结构里被 Asciidoctor 作为 level 1 section，输出仍应按模型 level 输出。这个规则要固定下来。

## 十三、如果我们只改 `.toSorted` 会不会引入风险

有风险，但可控。

现有单文件测试依赖的结构边，`nodeIndex.entries()` 的顺序和按 `startLine` 排序基本一致，所以应该不破坏。rootless top-level heading sibling 的测试也应该继续过，因为虚拟 document 的 children 顺序就是文档顺序。

主要风险在两个地方：

1. 如果某些人工构造的 `AbundantDocument` children 顺序不是 source order，改完后会按 children 顺序。这反而是正确的，因为 `AbundantDocument.children` 本来就是 parser 输出的文档结构顺序。
2. 如果有测试隐含依赖了 `heading-l1-o10` 这种字符串排序输出，那应该改测试，不应该让语义跟字符串排序绑定。

因此我认为第一步可以非常克制：先红测证明 bug，再把 `projectHeadingStructureEdges` 从 source-line sort 改成 document-order traversal。这个改动本身小，但语义很关键。

## 十四、最终理想答案

我现在的最终建议是：

1. 把现有 `aat:containsDirectly` / `aat:previousSibling` 修成真正的 logical document structure edges。这是根部治理，必须做。
2. 给每个 heading 加 `aat:documentOrder` 整数，让下游可以直接按全书阅读顺序排序。这是比依赖 TTL 文本顺序更正确的顺序模型。
3. 再加 `aat:bookOutlineRaw` 多行 literal，作为便捷投影。它不是替代结构边，而是从正确结构模型派生出来的消费捷径。
4. Turtle serializer 可以为了人类可读性按 document order 更友好地输出 heading subject，但不能把这个当机器契约。机器契约必须是 graph 里的 predicate/literal。

如果用一句话概括：

> TTL 可以排版成从上到下，但 RDF 必须显式建模顺序；book-entry 下结构顺序来自 logical document tree，origin source line 只用于回源，不用于排列书籍结构。

这才是理想状态。单独加字符串是补丁；修结构边加 `documentOrder` 是根治；在根治之后再加字符串，是对下游友好的缓存出口。

# 重新思考后的判断：底层投影应该提供有序标题树，不应该用字符串或 IRI 排序遮蔽模型

我重新想了一遍。你这次批评是对的，我前面的问题不是“不够谨慎”，而是把两个层次混在一起了：我一边说底层 RDF 图要显式建模顺序，一边又保留“TTL 打印顺序”和“`bookOutlineRaw` 字符串”作为设计点。这确实不干净。底层投影对象如果本来就是一个结构化数据投影，它应该把对象本身建完整，而不是先生成一个缺陷图，再附带一段渲染文本给下游绕过去。

我现在的判断有变化：

- TTL 文本从上到下排序不应该成为设计目标。它没有明确机器契约，也没有稳定消费者。可以作为调试输出的副作用，但不应该进入对象设计。
- `bookOutlineRaw` 不应该是核心 RDF projection 的主方案。它是一个渲染结果，不是底层结构事实。除非有明确产品接口要求“RDF 包里必须带一段 human-readable outline literal”，否则它应该放在 formatter/exporter 层，而不是拿来补 RDF 结构缺陷。
- 核心 RDF projection 应该输出一个完整、可查询、可验证的有序标题树。这个树本身足够让下游重建大纲、导航、查询父子关系和顺序。下游怎么渲染是下游自己的事情。

这次我会按对象本身来讲，不按“先做哪一步”来讲。

## 一、这个项目在这里提供的对象是什么

这里的对象不是“一个好看的 TTL 文件”，也不是“一个已渲染的大纲字符串”。这里的对象应该是：

> 从 AsciiDoc book-entry logical document 投影出的有序 heading tree，并且每个 heading node 保留可回源坐标。

这个对象有两个组成部分：

1. ordered heading tree：标题节点之间的父子关系、同父子节点顺序、整书遍历顺序。
2. origin source coordinate：每个标题对应的原始文件路径、原始行号范围、原始 raw slice。

这两个组成部分同属一个 heading projection，但不能互相替代。

- tree order 来自 logical document / Asciidoctor section tree。
- source coordinate 来自 origin line mapping。

当前代码错在把第二个对象拿去推第一个对象。`relativePath/startLine/endLine/raw` 是回源坐标，不是书籍结构顺序。多文件模式里，`startLine=1` 只是“这个标题在某个源文件第一行”，不表示“这个标题在全书第一”。

所以底层 projection 的完整性要求是：图里必须有足够事实表达 ordered heading tree。不能要求消费者从 origin line、IRI 字符串、TTL 文本顺序或 source file raw 里猜出书籍顺序。

## 二、IRI 的职责是什么

你问 IRI 是不是就是为了区分节点身份。我的判断：是的，IRI 的第一职责就是标识 RDF resource。它可以为了人类 debug 带一点可读痕迹，但不应该承载业务查询语义。

如果我们把顺序编码进 IRI，比如：

```text
#heading-0001-title
#heading-0002-preface
#heading-0003-part-one
```

然后让下游 `ORDER BY STR(?heading)`，这表面上很方便，但对象边界是坏的。

原因是：顺序是 heading 在某次 book projection 中的结构事实，不是 heading 身份本身。标题移动位置时，顺序改变；如果 IRI 也跟着顺序改变，那 resource identity 跟着移动而改变。这个后果是所有引用该 heading IRI 的边、缓存、diff、测试和外部存储都会把“移动位置”看成“旧节点消失、新节点出现”。这不是一个健康的数据模型。

当然，当前代码的 IRI 本来也不是完美稳定身份，它用了 `heading-l${startLine}-o${ordinal}`，行号变化也会改 IRI。但这只是当前实现的 synthetic local id 策略，不等于我们应该继续往 IRI 里塞更多语义。正确方向应该是减少消费者对 IRI 内部字符串的依赖，而不是鼓励消费者从 IRI 字符串读顺序。

所以我的明确判断是：

- IRI 必须唯一标识节点。
- IRI 可以可读，但应该被消费者当作 opaque identifier。
- 顺序必须用 RDF predicate/literal 表达，不应该藏在 IRI 字符串里。
- 如果未来要重做 resource identity，应考虑 source path + source heading coordinate + collision ordinal 或 stable generated id，而不是把 outline order 放进去。

这不是为了“省事”，而是因为把查询语义塞进标识符本身，会让标识符承担两个不同职责：身份和排序。这两个职责应该分开。

## 三、什么才是完整的 ordered heading tree

一个有序树至少需要三类事实。

第一，节点事实：

```ttl
?heading a aat:Heading ;
         aat:headline ?text ;
         aat:headingLevel ?level .
```

第二，父子事实：

```ttl
?parent aat:containsDirectly ?child .
```

第三，顺序事实。

这里我现在更倾向于不要只依赖 `previousSibling`。`previousSibling` 是一个合法的顺序表示，但它不是最直接的数据结构。消费者要取某个 parent 的 children，还需要：找所有 child，找没有 previousSibling 的链头，再沿反向 previousSibling 排列。这个能做，但作为底层数据投影，它把一个基本属性表达得太绕。

更直接的事实应该是同父子节点的 ordinal，例如：

```ttl
?child aat:siblingOrder 1 .
?child aat:siblingOrder 2 .
```

或者名字更准确一些：

```ttl
?child aat:childOrder 1 .
```

这个 predicate 的语义是：该 heading 在其 sibling group 中的 1-based 顺序。对于有 document title 的书，frontmatter/part/backmatter headings 是 document title 的 child，它们各自有 `childOrder`。对于 part 内 chapter，chapter 的 `childOrder` 是它在该 part 下的顺序。

同时，还应该有整书 preorder：

```ttl
?heading aat:documentOrder 1 .
?heading aat:documentOrder 2 .
?heading aat:documentOrder 3 .
```

`documentOrder` 的语义是：heading 在 logical document heading tree 的 preorder traversal 中的 1-based 顺序。document title 如果被投影成 heading，就占第 1 位。

这样底层数据是完整的：

- `containsDirectly` 表达树边。
- `childOrder` 表达同父排序。
- `documentOrder` 表达全书线性阅读顺序。
- `headingLevel` 表达 AsciiDoc/Asciidoctor 结构层级。
- `relativePath/startLine/endLine/raw` 表达回源坐标。

`previousSibling` 可以保留，但它应该成为从 `childOrder` 和 parent group 派生出的兼容关系，而不是唯一顺序来源。既然项目已有规约和测试把 `previousSibling` 当查询契约，那就继续输出它；但更完整的底层对象应该有 ordinal literal。

这不是在帮下游写渲染代码。`childOrder` 和 `documentOrder` 是 ordered tree 的构成性事实。没有它们，图里只有无序 child set 和 sibling link；可以重建，但不直接。加入它们不是越界，而是把底层数据结构表达完整。

## 四、`bookOutlineRaw` 现在应该如何看待

我改变了前面的想法。

如果这个库的 RDF projection 定位是“heading projection graph”，那么 `bookOutlineRaw` 不应该是 core graph 的必要字段。它是把有序 heading tree 渲染成 AsciiDoc heading lines 的一种视图。视图可以存在，但不应该替代 tree。

更合理的分层是：

- core RDF projection：提供 ordered heading tree。
- optional serializer/exporter：从 core graph 或 `AbundantDocument` 生成 `outline.adoc` 字符串。

如果某个下游工具明确只要字符串，可以调用 exporter。这个 exporter 可以和 CLI 集成成新 format，比如：

```bash
asciidoc-abundant-tree book.adoc --mode book-entry --format outline-adoc
```

或者在 JS API 里暴露：

```ts
serializeHeadingOutline(document)
```

但不应该默认塞进 RDF graph 作为“补救数据”。RDF graph 本身应该足够完整。否则以后会出现两个事实源：图结构说一个顺序，`bookOutlineRaw` 说另一个顺序。底层系统不应该制造这种双源一致性压力。

只有一种情况下我会接受把它写进 TTL：这个 RDF projection 的明确产品契约就是“同时携带 machine graph 和 human/rendered outline surface”。如果这么定，那 `bookOutlineRaw` 必须被定义成 derived literal，并且测试必须证明它由 `documentOrder/childOrder` 派生，而不是独立逻辑。否则我不建议把它作为核心设计。

所以更严格地说：你最开始提出“TTL 里单独存一份书籍全部大纲字符串”，这是一个可用需求表述，但从底层设计看，真正缺的是 ordered heading tree，不是字符串。字符串是一个消费形态；顺序树才是数据投影对象。

## 五、当前结构边应该怎样重构

现在的 `projectHeadingStructureEdges` 做了三件混在一起的事情：

1. 从 node index entries 取出标题节点。
2. 按 `startLine` 排序。
3. 用 heading level stack 重建父子和 sibling。

第二步是错误的。更深的问题是：它不应该在 RDF 阶段从坐标推断树。树已经在 `AbundantDocument.children` 里存在。

我认为重构后的结构应该是：

```text
AbundantDocument.children
  -> HeadingTreeProjectionPlan
  -> heading resources + nodeIndex entries
  -> structure triples
  -> order triples
  -> source coordinate triples
```

也就是说，先建立一个内部的 heading tree projection plan。这个 plan 里的每个节点有：

```ts
type HeadingProjectionNode = {
  node: TitleNode | SectionNode;
  parent?: HeadingProjectionNode;
  children: HeadingProjectionNode[];
  documentOrder: number;
  childOrder?: number;
};
```

然后 RDF projector 消费这个 plan：

- 给每个 plan node 创建 heading IRI。
- 写 heading facts。
- 如果有 parent，写 `parent containsDirectly child`。
- 如果有 childOrder，写 `child aat:childOrder N`。
- 写 `heading aat:documentOrder N`。
- 如果同父前一个 sibling 存在，写 `child aat:previousSibling previous`。

这样结构关系不再从 line span 推出来。line span 只参与 raw/source coordinate facts。

这是对象层面最清楚的架构：先有 heading tree plan，再有 RDF triples。不是“先打平，再用行号猜回树”。

## 六、是否还需要 `previousSibling`

需要保留，但我会重新定义它的位置。

`previousSibling` 是关系事实，表达“同父同级、当前 heading 的前一个 heading”。它对图遍历有价值，也已经在项目规约里存在。删除它会破坏既有查询契约。

但它不应该是唯一顺序事实。原因不是下游懒，而是 ordered tree 的 ordinal 是基本数据。一个 child 在 sibling group 中的位置，本身就是结构事实。`previousSibling` 是这个事实的一种边式表达；`childOrder` 是这个事实的一种数值表达。二者可以并存。

并存时必须有不变量：

- 同一个 parent 下，`childOrder` 从 1 开始连续递增。
- 第一个 child 没有 `previousSibling`。
- 第 N 个 child 的 `previousSibling` 指向同 parent 下 `childOrder = N - 1` 的 child。
- `previousSibling` 不跨 parent。
- `documentOrder` 是整棵树 preorder，不等于 `childOrder`。

这些不变量应该进入测试。不是为了覆盖率好看，而是因为这是 ordered tree 的本体约束。

## 七、测试应该怎么改才不是垃圾测试

现有测试有一个问题：很多测试直接用 `heading-l1-o0` 这种 local id 断言。这个对早期 projection 很方便，但它把测试绑在 resource id 生成细节上。结构测试应该尽量按语义找 heading，例如：

- 通过 `aat:headline` 找节点。
- 通过 `aat:addressLabel` 找节点。
- 通过 `aat:documentOrder` 找节点。

resource identity 的生成可以有自己的单元测试，但不应该支配结构语义测试。

新的测试体系应该分层：

### 1. Heading tree plan 测试

如果新增内部 plan builder，就直接测试：给一个 `AbundantDocument`，输出的 plan 是否有正确 parent、children、documentOrder、childOrder。

这类测试不碰 RDF serializer，不碰 IRI。

### 2. RDF structure tests

测试 RDF 图里是否存在：

- `containsDirectly`
- `previousSibling`
- `childOrder`
- `documentOrder`

这些测试通过 headline/addressLabel 定位节点，不通过 local id。

### 3. Book-entry multi-file regression

这个必须有。fixture 应该故意让多个文件的 heading 都在第 1 行或第 2 行，证明 projection 没有用 origin line 排序。

测试书应该包含：frontmatter、两个 part、part 内 chapter、backmatter index。这样才能覆盖“索引跑到第一部前面”这种错误。

### 4. Source coordinate tests

这些测试继续证明 `relativePath/startLine/endLine/raw` 来自 origin file。它们不应该断言结构顺序。

### 5. Serializer tests

如果保留 outline exporter，就测试 exporter。如果 core RDF 不带 `bookOutlineRaw`，就不要在 RDF serializer 测这个字符串。

这套测试不是“多不多”的问题，而是每类测试服务一个对象层：tree plan、RDF graph、book-entry regression、source coordinate、optional view。混在一起才会变成垃圾测试。

## 八、哪些代码应该移动、删除、改写

我认为应该做真实重构，而不是在原函数里继续堆条件。

### 应该删除或改写的东西

`projectHeadingStructureEdges` 里基于 `startLine` 排序的逻辑应该删除。不是改条件，不是 book-entry 特判，而是删掉这个错误推断来源。

```ts
.toSorted((left, right) => left.startLine - right.startLine)
```

这个规则不属于 heading structure edge。

### 应该新增的对象

新增一个内部 heading tree projection plan builder，例如：

```text
src/rdf12-projection/heading-tree.ts
```

它负责从 `AbundantDocument.title` 和 `AbundantDocument.children` 生成 ordered tree plan。

### 应该调整的 node index

`Rdf12NodeIndexEntry` 应该增加：

```ts
documentOrder: number;
childOrder?: number;
parent?: Rdf12IriTerm;
```

`parent` 是否放进 index 可以讨论。RDF 图里有 `containsDirectly`，但内部 index 如果有 parent，会让 payload/xref/label 等后续模块更容易按树语义工作。至少 `documentOrder` 和 `childOrder` 应该进入 index。

### 应该调整的 RDF facts

每个 heading 输出：

```ttl
aat:documentOrder N ;
```

非 root sibling 输出：

```ttl
aat:childOrder N ;
```

`document title` 是否有 `childOrder`：我倾向没有，因为它没有 parent。没有 document title 的 rootless top-level headings 可以有 `childOrder`，它们属于 implicit root sibling group；但如果不想引入 implicit root，也可以只给它们 `documentOrder` 和 `previousSibling`。这里需要规约明确。

我更干净的定义是：

- `documentOrder`：所有 heading 都有。
- `childOrder`：所有有 parent heading 的 heading 都有。
- rootless top-level headings 没有 parent heading，因此没有 `childOrder`，但它们之间仍有 `previousSibling` 和 `documentOrder`。

如果想表达 rootless top-level 的 group order，也可以引入 `aat:topLevelOrder`，但我不认为必要。

## 九、下游应该拿到什么，自己做什么

底层应该提供：

- heading 节点。
- heading 文本。
- heading 层级。
- heading 父子关系。
- heading sibling order。
- heading global document order。
- heading 回源坐标与 raw。
- labels/xref/payload 等既有事实。

下游应该自己做：

- 把 heading tree 渲染成 Markdown/AsciiDoc/HTML/IDE tree。
- 选择是否显示 frontmatter/backmatter。
- 折叠 part 或 chapter。
- 根据业务过滤 role/style。
- 把 RDF 图转成自己的导航模型。

底层不应该替下游做“outline string 是什么样”。如果有 exporter，那是另一个表面，不是 core graph 的必要事实。

这也修正了我前面的说法。前面我说 `bookOutlineRaw` 是为了让下游轻松，这个理由不够正。底层不是服务“轻松”，而是服务“事实完整”。如果事实完整，下游自然能做。如果事实不完整，下游写再多代码也只能猜。

## 十、我现在的最终设计判断

最终我会这样定义这个对象：

> RDF12 heading projection 是一个保留 origin source coordinate 的 ordered heading tree graph。它的结构顺序由 logical document heading tree 决定；它的 raw/source coordinate 由 origin line mapping 决定。Resource IRI 标识 heading node，不承载排序语义。排序语义由 `aat:documentOrder`、`aat:childOrder` 和 sibling relation 显式表达。

这句话里每个部分都有职责：

- “ordered heading tree graph”：核心对象是树，不是字符串。
- “origin source coordinate”：book-entry 回源事实仍然保留。
- “logical document heading tree”：结构顺序来源。
- “origin line mapping”：raw/source 坐标来源。
- “Resource IRI 标识 heading node”：IRI 职责。
- “不承载排序语义”：避免把查询语义藏进 ID。
- “显式表达”：RDF graph 内有顺序事实。

如果要重构，我会按这个定义改，而不是围绕 `bookOutlineRaw` 改。

## 十一、对我之前想法的修正

我之前保留了三个不该保留或至少不该放在核心层的东西。

第一，我不应该把 TTL 文本排序作为一个设计点。它没有可靠消费者，不是 graph contract。这个点应该删除。

第二，我不应该把 `bookOutlineRaw` 放在核心方案的中心。它可以是 view/exporter，不是 ordered tree 的替代品。

第三，我不应该用“最小修复”来回答“对象应该怎么设计”。实现可以分步骤，但设计讨论首先应该给出完整对象。否则就会变成你说的那种在承重结构没想清楚时讨论先糊哪块水泥。

我的修正后观点是：

- 根对象：ordered heading tree graph。
- 必要事实：parent-child、sibling/local order、global document order、heading level、headline、origin coordinate。
- 禁止依赖：TTL textual order、IRI lexical order、origin source line order。
- 可选导出：outline string。

这才是底层数据投影应该承担的边界。下游拿到这个图后，自己渲染大纲，自己选择 UI 或文本格式。底层不再伸手替下游做渲染，也不把不完整数据丢给下游猜。

# 重新按消费者、问题世界和对象边界审查后的判断

我读了你点名的 `observation-judgment-and-action/SKILL.md` 和那篇关于知识密集型协作中认知偏移的话语分析文档，也重新验证了本地代码里到底谁在消费 `previousSibling`、`containsDirectly` 等字段。先把最重要的修正放在前面：

这次我重新按这个标准审查。

## 一、当前问题到底是什么

当前问题不是“下游想偷懒”。当前问题是底层 RDF heading projection 没有给出可信的书籍有序结构，甚至在 book-entry 多文件场景里给出了错误结构。

已观察事实如下：

1. `asciidoc-abundant-tree` 在 book-entry 模式下已经构造 logical document，并且 `AbundantDocument.children` 里有正确的书籍结构顺序。
2. RDF projection 中的 heading `relativePath/startLine/endLine/raw` 是 origin source coordinate，用于回源，不是书籍阅读顺序。
3. 当前 `projectHeadingStructureEdges` 用 origin `startLine` 排序 heading entries，再生成 `containsDirectly` 和 `previousSibling`。
4. 多个 include 文件都有自己的第 1 行、第 2 行，因此 origin line 排序在 book-entry 下不能代表全书顺序。
5. 我在真实大样例里验证到错误：第一部 `从源文档看结构` 的 `previousSibling` 指向了 `索引`。这不是下游不会用，而是上游给错了。
6. 本地真实消费者 `micheng-ts/experiments/ttl-graph-viz/src/lib/ttl-parser.ts` 读取 `containsDirectly` 和 `previousSibling` 来构造 `documentRoot.children`。它的 `sortChildIds` 函数用 `previousSibling` 链排序 children。如果链断或错，它退回 `relativePath + startLine` 排序。这个退回规则在 book-entry 下同样不成立。

所以问题可以定义为：

> RDF heading projection 应提供可验证的 ordered heading tree；当前 projection 把 origin source coordinate 当成 document order，导致 book-entry 结构顺序错误，消费者无法从图中可靠取得书籍阅读顺序。

这个定义里没有“下游轻不轻松”，也没有“人看 TTL 方不方便”。它是底层数据契约不成立。

## 二、消费者是谁，消费者动作是什么

本地已经验证到一个真实消费者：`ttl-graph-viz`。

它的动作不是“读取测试”。它的动作是：

1. 用 `n3` 解析 TTL。
2. 找出所有 `aat:Heading`。
3. 读取 `aat:containsDirectly` 建立父子结构。
4. 读取 `aat:previousSibling` 给每个 parent 的 children 排序。
5. 生成 `DocumentNode` tree。
6. 左侧文档面板和图谱联动消费这个 tree。

这说明 `containsDirectly` 有明确消费者动作：构造文档树。

`previousSibling` 也有当前消费者动作：同父 children 排序。但这个动作本身不证明 `previousSibling` 是最佳字段；它只证明“顺序字段”有价值。`ttl-graph-viz` 不是在做“上一节导航”，也不是在展示“previous sibling relation”本身。它只是需要一个顺序依据。

因此，经过验证后我现在这样判断：

- `containsDirectly` 有不可替代价值。没有它，消费者拿不到树。
- “同父 children 的顺序”有不可替代价值。没有它，消费者拿不到有序树。
- `previousSibling` 这个具体 predicate 在当前观察范围内没有不可替代价值。它是现有顺序表达方式，但它服务的消费者动作可以由更直接的 `childOrder` 完成。
- `documentOrder` 有独立价值。它服务“按书籍阅读顺序取全体 headings”的动作，不等同于同父排序。

我只在本地 `micheng-ts` 搜索过，不能声称不存在外部 npm 消费者。这个未知不能直接授权保留字段；它只能被登记为外部兼容风险。如果你决定这个实验/项目不对外维持旧 RDF 契约，那就不应该因为未知外部消费者保留冗余字段。

## 三、我对 previousSibling 的修正判断

我收回前面的说法：`previousSibling` 不应该因为“已有测试/已有规约”而保留。

一个字段保留的条件应该是：它服务了 `containsDirectly + childOrder + documentOrder` 不能自然服务的消费者动作。当前没有观察到这个动作。

`previousSibling` 的成本也很清楚：

1. 它和 ordinal 顺序是重复表达。重复表达会制造一致性约束。
2. 如果 `childOrder` 说 A 是第 2 个 child，而 `previousSibling` 又指向错误节点，下游会面对两个事实源冲突。
3. 它让消费者为了排序要走链，而不是直接按数值排序。
4. 它当前已经被错误生成，说明它的维护路径容易被 source coordinate 混淆。

如果我们把 ordered heading tree 作为核心对象，顺序最直接的公共投影应该是 ordinal literal，而不是 sibling link。

所以我现在的设计结论是：

- 新 RDF heading projection 应以 `containsDirectly + childOrder + documentOrder` 表达有序树。
- `previousSibling` 不进入新的核心对象定义。
- 如果某个具体消费者将来需要“上一节/上一标题”的直接导航边，可以在该消费者侧由 `childOrder` 计算，或在另一个明确的 navigation projection 中生成。没有这个消费者动作时，不把它放进核心 RDF。
- 现有关于 `previousSibling` 的测试和文档应该被删除或改写，而不是被当作必须兼容的权威。

这不是为了激进删除，而是因为公共投影里的每一个字段都要有行动授权。当前已知动作是“排序 children”，`childOrder` 更直接满足它。

## 四、`childOrder` 和 `documentOrder` 为什么不是替下游写代码

底层不是要替下游渲染大纲，但底层必须把有序树表达完整。

一个普通无序树可以只给 parent-child relation。但书籍结构不是无序树。一本书的标题有阅读顺序。`前言` 在 `第一部` 前面，`索引` 在最后，这不是 UI 偏好，而是书籍对象的构成性事实。

因此，顺序不是下游加工出来的附加物。顺序是 source logical document 的结构事实。底层投影必须表达它。

`childOrder` 表达局部顺序：同一个 parent 下，第几个 child。

```ttl
:preface aat:childOrder 1 .
:part-one aat:childOrder 2 .
:index aat:childOrder 9 .
```

`documentOrder` 表达全局顺序：整本书 heading tree 的 preorder traversal 序号。

```ttl
:book-title aat:documentOrder 1 .
:preface aat:documentOrder 2 .
:part-one aat:documentOrder 3 .
:chapter-one aat:documentOrder 4 .
:index aat:documentOrder 20 .
```

这两个字段服务的是底层结构事实，不是 UI 渲染。下游仍然要自己决定：

- 是否渲染成 AsciiDoc outline。
- 是否显示 frontmatter。
- 是否折叠 part。
- 是否把 appendix 放单独区域。
- 是否生成 HTML TOC。
- 是否做 graph layout。

底层只承诺：这是一个有序 heading tree。

## 五、IRI 不应该承担排序语义

你提到可以让 IRI 按字符串排序得到书籍顺序。我认真想了，这个设计我不接受。

IRI 的公共职责是标识 resource。它可以有可读局部名，但消费者不应该从 IRI 字符串里解析业务事实。把顺序塞进 IRI，有三个问题。

第一，顺序会变化。章节移动时，如果 IRI 包含 order，那么同一个 heading occurrence 的 IRI 会因移动而变化。移动位置会变成“旧资源消失，新资源出现”。这会污染 diff、缓存、xref edge、graph layout 状态和外部存储。

第二，IRI 字符串排序不是 RDF 数据语义。让消费者 `ORDER BY STR(?heading)` 是把一个未声明的编码规则当成公共契约。这个规则藏在字符串里，不在 ontology 里，也不能自然验证。

第三，IRI 已经有唯一标识职责。如果再承担排序职责，身份和结构事实混在一起。以后想改 ID 生成策略，就会连带破坏顺序消费。

所以我的判断是：IRI 可以保持可读，但必须被消费者当作 opaque id。排序事实必须放在 `aat:childOrder` 和 `aat:documentOrder` 里。

当前 `heading-l1-o3` 这种 ID 本身也不理想，因为它带了 source line 痕迹。但它至少主要用于区分 resource。不要继续往这个方向增加排序语义。如果未来重做 ID，应该朝“稳定区分 resource”方向设计，而不是朝“字符串可排序”方向设计。

## 六、`bookOutlineRaw` 应该离开核心 RDF

我再次修正：`bookOutlineRaw` 不应该作为 core RDF heading projection 的设计点。

它对应的是一个渲染结果：把 ordered heading tree 投影成 AsciiDoc heading lines。这个结果可以有用，但它不是底层事实。

如果把它放进核心 RDF，会带来两个问题：

1. 它和 `containsDirectly/childOrder/documentOrder` 表达同一结构，形成重复事实源。
2. 它会让上游承担下游渲染格式选择。今天是 AsciiDoc outline，明天可能是 Markdown，后天可能是 HTML TOC。底层不应该选这个格式。

这不表示不能提供 outline。正确位置是 exporter，不是 core graph。

例如：

```ts
serializeHeadingOutline(graphOrDocument, { format: "adoc" })
```

或者 CLI：

```bash
asciidoc-abundant-tree book.adoc --format outline-adoc
```

这个 exporter 的消费者动作明确：需要一段文本大纲。它和 RDF graph 是两个公共投影，不应该互相混淆。

所以我现在不会把 `bookOutlineRaw` 作为核心设计。最初用户摩擦是“下游拿不到顺序”。真正解决是把 RDF 顺序建对，而不是把结果渲染好塞回 RDF。

## 七、`containsDirectly` 应该保留，而且应该更严格

`containsDirectly` 的消费者动作已经明确：构造树。

它不能被 `documentOrder` 替代。`documentOrder` 只能给全局线性顺序，不能告诉某个 chapter 属于哪个 part。`childOrder` 也不能单独表达父子关系。书籍 heading structure 至少需要 parent-child relation。

因此 `containsDirectly` 是核心字段。它的规则应改成：

- subject 和 object 都必须是 `aat:Heading`。
- subject 是 object 在 logical document heading tree 中的直接 parent。
- 不表达传递闭包。
- 不连接 paragraph/listing/table/payload/xref/label。
- 不从 source line 推断。
- 不从 RDF serializer 文本顺序推断。
- 直接由 parser/Asciidoctor 提供的 `AbundantDocument.children` 树生成。

大样例里：

- 书名 contains `摘要`、`版本说明`、`献辞`、`前言`、`致谢`、三个 part、appendix、glossary、bibliography、index。
- `从源文档看结构` contains `源文本与投影`、`标题与引用`、`源文件编排号`。
- root 不直接 contains 这些 part 内 chapter。

这才是树。

## 八、上游 asciidoc-abundant-tree 应该如何重构

我现在认为上游应该引入一个明确的内部对象：`HeadingTreeProjection`。

它不是为了未来扩展，也不是包装现有代码。它是为了把当前混在一起的两个事实拆开：结构事实和回源事实。

形状可以是：

```ts
type HeadingTreeEntry = {
  node: TitleNode | SectionNode;
  parent: HeadingTreeEntry | undefined;
  children: HeadingTreeEntry[];
  documentOrder: number;
  childOrder: number | undefined;
};
```

构造规则：

1. 从 `AbundantDocument.title` 创建 title heading entry，如果存在。
2. 递归遍历 `AbundantDocument.children`。
3. 只接收 `kind === "section"` 的节点进入 heading tree。
4. 非 heading block 不进入 tree，但它仍然存在于 `AbundantDocument` 用于 raw、payload、xref 等投影。
5. 每个 parent 的 section children 按 `children` 数组顺序分配 `childOrder`。
6. 整棵树按 preorder 分配 `documentOrder`。

RDF projection 消费这个 tree：

- 为每个 entry 创建 heading resource。
- 写 `headline/headingLevel/raw/source coordinate`。
- 写 `documentOrder`。
- 如果有 parent，写 `parent containsDirectly child` 和 `childOrder`。

不要再让 `structure-projector` 打平 headings 后按 `startLine` 重建树。这个算法应该删除。

`startLine/endLine` 的用途只保留在回源字段里。它不参与结构排序。

## 九、下游 ttl-graph-viz 应该如何变化

既然我已经验证 `ttl-graph-viz` 是真实消费者，它也应该跟着新契约改。

当前 `ttl-parser.ts` 的 `sortChildIds` 使用 `previousSibling`：

```ts
const previous = firstObjectValue(store, childId, `${AAT}previousSibling`);
```

新契约下应该改成：

```ts
sort children by numeric aat:childOrder
```

如果某个 child 缺少 `childOrder`，这就是上游数据错误或非树内 heading，不应该退回 `relativePath/startLine` 猜。退回猜测会重新把错误藏起来。实验项目里我们不需要宽容错误数据；它应该直接暴露诊断，或者把 child 放到 unknown order 区并报错。

`documentOrder` 则用于：

- 全局标题列表。
- 搜索结果按书籍顺序排列。
- graph layout 初始顺序。
- 没有 parent 的 rootless headings 的线性排序。

`ttl-graph-viz` 不应该继续通过 `relativePath + startLine` 推断阅读顺序。那是 source coordinate，不是 book order。

这就是上下游职责分离：

- 上游投影给 ordered heading tree facts。
- 下游读取这些 facts 构建 UI。
- 下游不从 IRI、TTL 文本、source line 猜顺序。

“兼容”不是设计理由。只有明确消费者依赖，兼容才有对象。

## 十三、最终我会怎么设计

如果让我现在给出干净设计，我会这样写规约：

### RDF12 heading projection

RDF12 heading projection 是从 `AbundantDocument` 生成的有序标题树图。它把 AsciiDoc document title 和 section headings 投影为 `aat:Heading` resources。

### Heading identity

每个 heading resource 表示一次文档标题或 section heading occurrence。IRI 只标识 resource，不定义排序、层级或回源语义。排序、层级和回源必须由显式 predicates 表达。

### Tree relation

`aat:containsDirectly` 表示 heading tree 中的直接父子关系。它只连接 heading resources，不表达传递闭包。

### Local order

`aat:childOrder` 表示 heading 在其 parent heading 的直接 children 中的 1-based 顺序。拥有同一 parent 的 children 的 `childOrder` 必须连续且唯一。

### Global order

`aat:documentOrder` 表示 heading 在 logical document heading tree preorder traversal 中的 1-based 顺序。所有 heading resources 必须有唯一 `documentOrder`。

### Source coordinate

`aat:relativePath`、`aat:startLine`、`aat:endLine`、`aat:headingLine`、`aat:raw` 描述 origin source file 中的 heading slice。它们不参与 tree order 计算。

### Book-entry rule

book-entry projection 的 tree relation 和 order 来自 logical document section tree；source coordinate 来自 line origin 映射后的 origin source file。实现不得用 origin source line order 重建 logical document order。

### Removed relation

`aat:previousSibling` 不属于核心 heading projection。相邻 sibling 可由同 parent 的 `childOrder` 推导。若某个消费者需要直接上一 sibling 导航，应由消费者或单独 navigation projection 从 `childOrder` 派生。

这套规约里没有“兼容”。每个字段都有消费者动作和对象职责。

第六层是验证标准。好的文档必须能导出测试。这里要写出必须通过的对象不变量：`documentOrder` 连续唯一、同父 `childOrder` 连续唯一、`containsDirectly` 只连 heading、source coordinates 不参与 order、book-entry 多文件相同行号不破坏顺序、下游不再 fallback 到 source line 猜 order。

我给自己的质量标准是：

1. 文档中每个公共字段都能回答“服务哪个消费者动作”。答不出就不进核心对象。
2. 文档中每个“禁止”都对应已经发生或高风险发生的误读，例如用 IRI 排序、用 TTL 文本顺序排序、用 origin line 排序。
3. 文档不使用“兼容已有测试”作为设计理由。测试只从对象规约派生。
4. 文档区分上游 projection 和下游 rendering。上游给有序 heading tree；下游官方 HTML 阅读视图从 SourceFile 重建虚拟文件系统交给 Asciidoctor，不从 heading raw 拼全文。
5. 开发者能直接定位代码：`structure-projector.ts`、`node-index.ts`、新增 heading tree plan、相关测试和文档。
6. 文档允许破坏性变更，并明确哪些旧字段/旧测试/旧假设应删除。
7. 文档不把未来可能性写成当前承诺。`bookOutlineRaw`、RDF List、IRI sortable local id 都归档为非核心或未来对象，不进入当前核心规约。

== 1. 文档身份

本文定义 `asciidoc-abundant-tree` RDF12 heading projection 的有序标题树重设计。

本文不是实施计划。本文不定义工期、批次、提交顺序或人员安排。本文定义当前问题、目标对象、公共字段、生成规则、消费者边界、删除项和验证标准。

本文面向下一位开发者。开发者可以结合当前代码阅读本文，并据此修改实现、测试和文档。

== 2. 当前问题世界

`asciidoc-abundant-tree` 支持 single-file 和 book-entry 两种输入模式。

single-file 模式中，源文档是一份物理 AsciiDoc 文件。heading 的 source line order 与 document order 通常一致。

book-entry 模式中，entry file 通过 `include::...[]` 组织多文件书稿。系统先构造 source-mapped logical document，再由 Asciidoctor 解析 logical text。logical document 提供书籍结构顺序；line origin 提供回源坐标。

当前 RDF12 heading projection 已经输出 heading resources、`aat:containsDirectly`、`aat:previousSibling`、heading raw、source coordinates、source files、xref edges 等事实。

当前错误发生在 heading structure edge 生成阶段。`src/rdf12-projection/structure-projector.ts` 中的 `projectHeadingStructureEdges` 从 `nodeIndex.entries()` 取 heading entries 后，按 `entry.startLine` 排序，再用 heading level stack 重建父子与兄弟关系。

该规则在 book-entry 模式下不成立。`entry.startLine` 是 origin source file 内的行号。多个 included files 都可以从第 1 行开始。origin source line order 不是 logical document order。

在 `07-structured-writing-conventions` 真实书籍样例中，当前 RDF 输出出现错误：第一部 `从源文档看结构` 的 `aat:previousSibling` 指向 `索引`。该关系违反书籍阅读顺序，也违反同父 sibling 顺序。

该错误不是下游消费方式不足。该错误是 projection 输出了错误结构事实。

== 3. 已验证消费者

本地已验证消费者为 `micheng-ts/experiments/ttl-graph-viz`。

该消费者读取 TTL 后执行以下动作：

* 解析 RDF graph。
* 收集 `aat:Heading` nodes。
* 读取 `aat:containsDirectly` 构造 document tree。
* 读取 `aat:previousSibling` 对同父 children 排序。
* 生成 `DocumentNode` tree。
* 用该 tree 支持左侧文档栏和图谱联动。

该消费者证明两个消费者动作成立：

* 需要父子关系来构造文档树。
* 需要同父 children 顺序来构造有序文档树。

该消费者没有证明 `aat:previousSibling` 这个具体 predicate 不可替代。它只证明“顺序事实”不可缺失。当前 `previousSibling` 的实际用途是排序 children，不是上一节导航、编辑操作、差异比较或其它独立动作。

当前未验证外部 npm 消费者。未知外部消费者不能作为字段准入理由。若项目所有者决定发布破坏性版本，应以新对象规约为准，并在 release notes 中明确破坏性变更。

== 4. 期望改变

重设计后的 RDF12 heading projection 必须提供可查询、可验证、来源清晰的 ordered heading tree graph。

消费者应能从 RDF graph 中取得：

* 所有 heading nodes。
* 每个 heading 的标题文本和层级。
* heading tree 的直接父子关系。
* 每个 parent 下 children 的局部顺序。
* 整本书的全局 heading 阅读顺序。
* 每个 heading 的 origin source coordinate 和 raw slice。

消费者不得需要从以下表面推断书籍顺序：

* TTL 文本中 triples 的排列顺序。
* Turtle object list 的书写顺序。
* IRI 字符串的字典序。
* origin source file line number。
* source file path 字典序。
* `aat:raw` 字符串拼接结果。

== 5. 目标对象

RDF12 heading projection 是从 `AbundantDocument` 生成的有序标题树图。

该图的核心对象是 heading occurrence。document title 和 section heading 都可以成为 heading occurrence。

该图同时表达两类事实：

* logical structure facts：父子关系、局部顺序、全局顺序、heading level、headline。
* origin source facts：relative path、source line span、heading line、raw slice。

logical structure facts 来自 `AbundantDocument.title` 和 `AbundantDocument.children` 所表示的 logical document heading tree。

origin source facts 来自 source coordinate recovery 和 line origin 映射。

实现不得用 origin source facts 推导 logical structure facts。

== 6. 字段准入规则

公共 RDF 字段进入 heading projection 前必须满足表面单位准入条件：

* 它服务明确消费者动作。
* 它表达当前对象的事实，而不是实现历史。
* 它不能由其它字段无损、低成本、无歧义地替代，除非存在独立消费者动作。
* 它有可验证不变量。
* 它不会制造两个可冲突的事实源。

内部测试、旧实现、旧文档和历史输出不能单独授权字段保留。

== 7. Heading resource 身份

每个 heading resource 表示一次 document title 或 section heading occurrence。

IRI 的职责是标识 resource。IRI 不定义排序、层级、父子关系或回源语义。

消费者不得通过解析 IRI 字符串取得业务事实。消费者不得通过 `ORDER BY STR(?heading)` 获取书籍顺序。

IRI 可以保持人类可读，但其内部格式是 resource identity strategy，不是 heading projection ontology。

当前 `heading-l${startLine}-o${ordinal}` local id 可以暂时保留，以降低同一版本内其它模块的变更面。但新顺序语义不得继续写入 IRI。

若未来重做 resource identity，应以稳定区分 heading occurrence 为目标，而不是以 IRI 字符串排序为目标。

== 8. Heading node facts

每个 heading resource 必须输出：

[source,turtle]
----
?heading a aat:Heading .
?heading aat:headline ?headline .
?heading aat:headingLevel ?level .
?heading aat:documentOrder ?documentOrder .
----

`aat:headline` 是读者可见标题文本。

`aat:headingLevel` 是 Asciidoctor/AsciiDoc heading level。document title 使用 level 0。book doctype 中的 part 也可能是 level 0 section。

`aat:documentOrder` 是全局 heading 顺序。其规则见第 11 节。

有 source coordinate 的 heading 还应输出 source facts。source facts 的规则见第 13 节。

== 9. 父子关系：aat:containsDirectly

`aat:containsDirectly` 表达 heading tree 中的直接父子关系。

[source,turtle]
----
?parent aat:containsDirectly ?child .
----

规则：

* subject 必须是 `aat:Heading`。
* object 必须是 `aat:Heading`。
* relation 只表达直接父子关系，不表达传递闭包。
* relation 不连接 paragraph、listing、table、payload、xref edge、label、source file 或普通 attribute resource。
* relation 来自 logical document heading tree，不来自 source line sort。
* relation 的 sibling order 由 `aat:childOrder` 表达，不由 Turtle object list 顺序表达。

有 document title heading 时，document title heading 是顶层 sections 的 parent。

无 document title heading 时，顶层 sections 没有 parent heading。实现不得制造虚构 document heading 来填补 parent。

== 10. 局部顺序：aat:childOrder

`aat:childOrder` 表示 heading 在其 parent heading 的直接 children 中的 1-based 顺序。

[source,turtle]
----
?child aat:childOrder 1 .
?child aat:childOrder 2 .
----

规则：

* 只有存在 parent heading 的 heading 才输出 `aat:childOrder`。
* 同一 parent 下的 children 的 `aat:childOrder` 必须从 1 开始连续递增。
* 同一 parent 下不得存在两个 child 拥有相同 `aat:childOrder`。
* `aat:childOrder` 的排序依据是 parent 的 `children` 数组顺序。
* `aat:childOrder` 不从 origin source line、relativePath 或 IRI 推导。

消费者通过 `containsDirectly` 取得 parent 的 children 后，应按 `childOrder` 排序。

若 parent-child triple 存在而 child 缺少 `childOrder`，该 projection 不满足 ordered tree contract。

== 11. 全局顺序：aat:documentOrder

`aat:documentOrder` 表示 heading 在 logical document heading tree preorder traversal 中的 1-based 顺序。

规则：

* 所有 heading resources 必须输出 `aat:documentOrder`。
* 每个 `aat:documentOrder` 在同一 projection 内唯一。
* `aat:documentOrder` 必须从 1 开始连续递增。
* document title heading 如果存在，必须拥有 `documentOrder = 1`。
* traversal 顺序为：当前 heading，然后按 `childOrder` 递归访问 children。
* 无 document title heading 时，顶层 sections 按 `AbundantDocument.children` 中的出现顺序进入 traversal。

消费者需要整本书线性大纲时，应按 `aat:documentOrder` 排序。

`aat:documentOrder` 不替代 `aat:containsDirectly`。它只能表达线性 traversal，不能单独表达父子结构。

== 12. 移除关系：aat:previousSibling

`aat:previousSibling` 不属于重设计后的核心 heading projection。

理由：

* 当前已验证消费者只用它排序同父 children。
* `aat:childOrder` 更直接表达同一消费者动作。
* `previousSibling` 与 ordinal order 重复，增加一致性成本。
* 当前错误正发生在 sibling relation 生成路径中。
* 没有观察到必须直接消费 previous sibling edge 的本地消费者动作。

新版本应停止输出 `aat:previousSibling`。

旧测试中关于 `aat:previousSibling` 的断言应删除或改写为 `aat:childOrder` / `aat:documentOrder` 断言。

旧文档中把 `aat:previousSibling` 定义为核心查询契约的内容应修改。若需要保留历史说明，应放入迁移说明或实现历史，不得继续作为当前对象规约。

若未来出现明确消费者动作，例如“上一节导航必须由图中直接边支持”，该需求应作为新事实重新评估。不能以未知未来保留当前字段。

== 13. Source coordinate facts

source coordinate facts 描述 heading 在 origin source file 中的回源位置。

常见字段包括：

[source,turtle]
----
?heading aat:relativePath ?path .
?heading aat:startLine ?startLine .
?heading aat:endLine ?endLine .
?heading aat:headingLine ?headingLine .
?heading aat:raw ?raw .
----

规则：

* `aat:relativePath` 是 origin source file path，不是 logical document path。
* `aat:startLine` 和 `aat:endLine` 是 origin source file 内 line span。
* `aat:headingLine` 是 origin source file 内 heading line。
* `aat:raw` 是 origin source file 中该 heading slice 的原文。
* book-entry 模式不得把 logical text 当作 `aat:raw` 来源。
* source coordinate facts 不参与 heading tree order 计算。

book-entry 下，entry file 中 part heading 的 raw 可以包含 include directive，因为 include directive 是 entry file 原文。

included file 中 chapter heading 的 raw 来自 included file 原文。

== 14. Book-entry 规则

book-entry projection 必须分离 logical structure 和 origin coordinate。

logical structure 来源：

* include resolution 后的 logical text。
* Asciidoctor 对 logical text 生成的 section tree。
* `AbundantDocument.title` 和 `AbundantDocument.children`。

origin coordinate 来源：

* `LogicalSource.lineOrigins`。
* origin source file line tables。
* source coordinate recovery。

禁止规则：

* 不得按 origin `startLine` 排序 heading tree entries。
* 不得按 `relativePath` 字典序排序 book headings。
* 不得用 source file raw 的扫描顺序替代 logical document order。
* 不得用 Asciidoctor include sourcemap 替代 book-entry line origin contract。
* 不得从 `aat:SourceFile` raw 重新 parse heading tree 来修复 RDF structure edge。

`aat:SourceFile` 服务官方渲染、回源、诊断和 source retention。它不替代 heading tree projection。

== 15. Single-file 规则

single-file projection 同样使用 `AbundantDocument.title + children` 构造 heading tree。

single-file 中 source line order 与 document order 通常一致，但实现仍不得依赖 source line sort 作为结构算法。

统一规则：所有模式下，结构关系和顺序都来自 `AbundantDocument` heading tree。

== 16. 内部生成对象：HeadingTreeProjection

实现应引入内部对象 `HeadingTreeProjection` 或等价结构。

建议形状：

[source,typescript]
----
type HeadingTreeEntry = {
  readonly node: TitleNode | SectionNode;
  readonly parent?: HeadingTreeEntry;
  readonly children: HeadingTreeEntry[];
  readonly documentOrder: number;
  readonly childOrder?: number;
};
----

构造规则：

* document title 存在时，先创建 title entry。
* title entry 的 `documentOrder` 为 1。
* title entry 没有 `childOrder`。
* 递归遍历 `AbundantDocument.children` 中的 section nodes。
* 只把 `kind === "section"` 的 nodes 放入 heading tree。
* 非 heading nodes 不进入 heading tree。
* parent 的 section children 按 `children` 数组出现顺序分配 `childOrder`。
* 全树按 preorder 分配 `documentOrder`。

RDF projector 应消费该内部对象生成 triples。

== 17. `structure-projector.ts` 设计要求

`structure-projector.ts` 应停止从 node index entries 的 source coordinates 推断结构。

当前错误模式应移除：

[source,typescript]
----
context.nodeIndex.entries().toSorted((left, right) => left.startLine - right.startLine)
----

替代设计：

* 从 `AbundantDocument` 构造 `HeadingTreeProjection`。
* 按 `HeadingTreeProjection` 创建 heading resources。
* 写 heading node facts。
* 写 source coordinate facts。
* 写 `documentOrder`。
* 对每个有 parent 的 entry 写 `containsDirectly` 和 `childOrder`。

`nodeIndex` 可以继续用于 xref、label、payload 等 downstream projection lookup，但 index entries 应携带 `documentOrder` 和 `childOrder`。

== 18. `node-index.ts` 设计要求

`Rdf12NodeIndexEntry` 应增加 ordering fields。

建议字段：

[source,typescript]
----
type Rdf12NodeIndexEntry = {
  readonly node: TitleNode | SectionNode;
  readonly iri: Rdf12IriTerm;
  readonly localId: string;
  readonly kind: "document-title" | "section";
  readonly documentOrder: number;
  readonly childOrder?: number;
  readonly relativePath?: string;
  readonly sourceStartLine?: number;
  readonly sourceEndLine?: number;
  readonly startLine: number;
  readonly endLine: number;
  readonly targetType: "section";
};
----

`findByTarget` 不应使用 `documentOrder`。target lookup 仍按 target type 和 source span / label catalog 执行。

`entries()` 返回 entries 时不承担排序语义。需要排序的消费者应显式使用 `documentOrder`。

== 19. 下游 `ttl-graph-viz` 消费规则

`ttl-graph-viz` 应改为消费 `aat:childOrder` 和 `aat:documentOrder`。

规则：

* 构造 `containsMap` 后，children 按 numeric `aat:childOrder` 排序。
* 不再读取 `aat:previousSibling`。
* 不再 fallback 到 `relativePath + startLine` 推断 children order。
* 若 parent 的 child 缺少 `childOrder`，parse 层应产生诊断或测试失败。
* 全局 heading 列表按 `documentOrder` 排序。
* graph layout、搜索结果、文档树默认顺序应使用 projection order facts。

`ttl-graph-viz` 官方 HTML 阅读视图应从 `aat:SourceFile` 重建 virtual source document，并交给 Asciidoctor.js include processor。该渲染路径不从 heading raw 拼接整书。

== 20. `bookOutlineRaw` 非核心规则

`bookOutlineRaw` 不进入核心 RDF heading projection。

理由：

* 它是 ordered heading tree 的文本渲染结果，不是底层结构事实。
* 它与 `containsDirectly + childOrder + documentOrder` 重复表达同一结构。
* 它会引入双事实源一致性成本。
* 它把输出格式选择提前放进底层 graph。

若需要文本大纲，应提供单独 exporter 或 CLI format，例如 `outline-adoc`。该 exporter 从 ordered heading tree 生成文本，不反向定义 core RDF graph。

== 21. TTL 文本顺序非目标

Turtle serialization 的 triple 排列顺序不属于机器消费契约。

不得要求消费者通过 TTL 文件中 triples 的从上到下顺序取得书籍顺序。

Turtle writer 可以为了调试可读性按 `documentOrder` 分组输出 headings，但这只是显示策略，不是数据模型。

当前核心设计不要求修改 Turtle writer 输出顺序。

== 22. RDF List 非当前目标

RDF List 可以表达 ordered collection，但不作为当前核心设计。

理由：

* 当前消费者需要树结构和排序，不需要 RDF collection surface。
* `containsDirectly + childOrder + documentOrder` 已能表达所需事实。
* RDF List 增加 `rdf:first/rest/nil` 处理成本。
* 项目现有 graph/JSON-LD serializer 没有围绕 RDF collection 建模。

若未来有明确 RDF collection 消费者，可重新评估。

== 25. 验证不变量

RDF projection 必须满足以下不变量。

=== 25.1 Heading type invariant

所有 `aat:containsDirectly` 的 subject 和 object 都是 `aat:Heading`。

=== 25.2 Parent-child invariant

`?parent aat:containsDirectly ?child` 当且仅当 `child` 是 logical heading tree 中 `parent` 的直接 child。

=== 25.3 Child order invariant

同一 parent 的所有 direct children 必须拥有唯一、连续、1-based `aat:childOrder`。

=== 25.4 Document order invariant

所有 heading resources 必须拥有唯一、连续、1-based `aat:documentOrder`。

=== 25.5 Traversal invariant

按 `aat:documentOrder` 排序得到的 headings 必须等于 logical heading tree preorder traversal。

=== 25.6 Source coordinate separation invariant

改变 source file path 或 origin line collisions 不得改变 logical heading order。多个 included files 的 heading 都位于第 1 行时，`documentOrder` 和 `childOrder` 仍必须正确。

=== 25.7 No hidden order invariant

测试不得通过 IRI lexical order、TTL textual order、relativePath sort 或 startLine sort 来证明 document order。

=== 25.8 Removed predicate invariant

新 projection 不输出 `aat:previousSibling`。若某测试仍要求该 predicate，该测试应被视为旧契约残留。

== 28. 与 SourceFile 官方渲染的关系

SourceFile 官方渲染是相邻对象，不是 heading tree projection 的替代品。

`aat:SourceFile` resources 保存原始文件集合。book-entry 下，entry file raw 保留 include directives。官方 HTML 阅读视图应从 `aat:SourceFile` 重建 virtual filesystem，并交给 Asciidoctor.js include processor。

heading tree projection 服务 graph/query/navigation。

SourceFile rendering 服务 official HTML reading surface。

下游可以同时消费二者：

* 用 ordered heading tree 建图谱、目录、节点联动。
* 用 SourceFile virtual filesystem 生成官方 HTML。

不得用 heading raw 拼接完整书籍 HTML。heading raw 是 heading slice，不是完整 source document。

== 29. Breaking change 声明

本设计是破坏性变更。

破坏性变化：

* 停止输出 `aat:previousSibling`。
* 新增必需排序字段 `aat:documentOrder`。
* 新增 parent-scoped 排序字段 `aat:childOrder`。
* 消费者必须从 `childOrder/documentOrder` 获取顺序。
* 旧的 source-line order fallback 不再被视为合法消费策略。

release notes 应说明迁移方式：

* 使用 `aat:containsDirectly` 取得 children。
* 使用 `aat:childOrder` 对 children 排序。
* 使用 `aat:documentOrder` 获取全局 heading order。
* 不再使用 `aat:previousSibling`。

== 30. 完成定义

重设计完成必须满足：

* RDF heading projection 的结构和顺序来自 `AbundantDocument` heading tree。
* Origin source coordinates 不参与 heading order。
* `aat:containsDirectly` 正确表达直接父子关系。
* `aat:childOrder` 正确表达同父顺序。
* `aat:documentOrder` 正确表达全局 preorder。
* 新 projection 不输出 `aat:previousSibling`。
* Book-entry 多文件相同行号 fixture 通过。
* Single-file projection 仍通过 ordered tree contract。
* Source coordinate tests 仍证明 raw 回 origin file。
* `ttl-graph-viz` 改为消费 `childOrder/documentOrder`。
* 文档和 release notes 反映破坏性变更。

== 31. 核心判断

当前错误不是下游使用不当，而是 RDF heading projection 未正确表达 ordered heading tree。

正确修复不是给 TTL 排版，不是改 IRI 字符串，不是塞入 `bookOutlineRaw`，也不是让下游继续 fallback 到 source line。

正确修复是把 ordered heading tree 作为 projection 的核心对象：

* 树由 `containsDirectly` 表达。
* 同父顺序由 `childOrder` 表达。
* 全书顺序由 `documentOrder` 表达。
* 回源由 source coordinate fields 表达。
* IRI 只表达 resource identity。

该设计使底层数据完整，下游可以自行构建目录、导航、图谱、渲染和分析视图。
