# asciidoc-abundant-tree 描述列表 AST 异常调查结论

我已经把这个现象复现并定位到比较明确的根因。结论先说：这个样例里的描述列表语法本身被 Asciidoctor 正常识别了，问题不是 `Host::` / `数据库:::` / `初始大小;;` 这些语法没有被解析；真正的问题在 `asciidoc-abundant-tree` 当前的官方 AST walker 对 `dlist` 的子节点模型做了错误假设。它把 `dlist.getBlocks()` 返回的每个元素都当成普通 Asciidoctor Block 递归处理，但 Asciidoctor 的描述列表条目不是普通 block 数组，而是 tuple/array 结构，所以 walker 走到数组时调用不到 `getContext()`、`getNodeName()`、`getSourceLocation()`，于是产生了你看到的一串 `context='undefined' node='undefined' source-location.missing` 诊断。

## 复现现象

你运行：

```bash
asciidoc-abundant-tree 描述列表.adoc
```

当前输出里只有 document/title/sourceText，没有 children：

```text
children[]
targets[]
xrefOccurrences[]
anchorOccurrences[]
toolDiagnostics[]
  official-block-context.unknown ... context 'undefined'
  source-location.missing ... node 'undefined'
```

我在项目源码下用本地 `pnpm exec tsx src/cli.ts samples/tmp/描述列表.adoc` 复现，输出和你贴的一致。说明这个不是全局安装版本偶发，而是当前项目实现对这个输入稳定复现。

## Asciidoctor 原始 AST 实际长什么样

我绕过本项目转换层，直接用 `@asciidoctor/core` 3.0.4 加载同一个文件并打印 `getBlocks()`。第一层结果是：

```text
document ctx=document line=1 blocks=1
  dlist ctx=dlist line=4 blocks=4
```

这说明 Asciidoctor 第一层已经把第 4 行开始的内容识别成 `dlist`，不是普通段落，也不是解析失败。

然后继续展开 `dlist.getBlocks()`，关键结构如下：

```text
dlist line=4 blocks=4
  Array len=2
    [0] Array len=1
      list_item line=4 text="Host"
    [1] list_item line=4 text="127.0.0.1"
  Array len=2
    [0] Array len=1
      list_item line=5 text="Port"
    [1] list_item line=5 text="8080"
  Array len=2
    [0] Array len=1
      list_item line=6 text="Timeout"
    [1] list_item line=6 text="3000ms"
  Array len=2
    [0] Array len=1
      list_item line=8 text="系统总配置 (System Configuration)"
    [1] list_item line=9 text="这里定义了整个后台运行环境的基础参数。" blocks=1
      dlist line=11 blocks=2
```

也就是说，描述列表每一项不是一个普通 Block，而是：

```text
[[termItem1, termItem2, ...], descriptionItem]
```

嵌套描述列表挂在 descriptionItem 的 `getBlocks()` 下面。比如第 8 行“系统总配置”对应的 description item 在第 9 行，并且它下面挂了第 11 行开始的内部 `dlist`。这个结构和 HTML 输出完全一致：Asciidoctor 能正常渲染成 `<dl><dt>...</dt><dd>...</dd></dl>`，嵌套也正常。

## 官方资料佐证

我查了 Asciidoctor 官方文档，最相关的是 “Find Blocks” 页面：

https://docs.asciidoctor.org/asciidoctor/latest/api/find-blocks/

里面明确说明两点：

1. `find_by` 是推荐的块查找方法，因为它会替调用者处理不同 block model 的差异。
2. 自己从 `Document.blocks` / `getBlocks()` 往下走也可以，但不是所有 block 都有同一种模型；文档特别举例说 description list 的每一项是两个节点组成的数组。

另一个 `@asciidoctor/core` API 文档也有对应说法：

https://asciidoctor.github.io/asciidoctor.js/main/classes/Block.html

我本地验证 `doc.findBy({})` 也证明这一点。直接 `findBy` 能返回完整的扁平 block 序列，包括全部 `dlist` 和 `list_item`：

```text
document line=1
section line=1
dlist line=4
list_item line=4 text="Host"
list_item line=4 text="127.0.0.1"
list_item line=5 text="Port"
list_item line=5 text="8080"
...
dlist line=21
list_item line=21 text="引擎 (Engine)"
list_item line=21 text="Redis"
list_item line=22 text="集群模式 (Cluster Mode)"
list_item line=22 text="启用 (true)"
```

所以官方的 `findBy` 能看见这些节点；当前项目自己的 `walkOfficialBlocks` 看不见，是因为它没有处理 `dlist` 的 tuple 模型。

## 代码层根因

问题集中在：

`micheng-ts/projects/asciidoc-abundant-tree/src/official-block-walker.ts`

当前核心逻辑是：

```ts
surface.children = (block.getBlocks?.() ?? []).map((child, index) =>
    walkBlock(child, surface, index),
);
```

这段代码隐含了一个假设：`block.getBlocks()` 返回的每个 `child` 都是 `AsciidoctorBlock`。对普通 `section`、`open`、`listing`、`table` 等很多场景这个假设基本成立；但对 `dlist` 不成立。`dlist.getBlocks()` 返回的是数组条目，每个条目大致是 `[[terms], description]`。于是 `walkBlock(child, ...)` 收到的是 JavaScript `Array`，不是 Asciidoctor block。

数组当然没有 `getContext()`、`getNodeName()`、`getSourceLocation()`。在 `walkBlock` 内部：

```ts
context: block.getContext?.(),
nodeName: block.getNodeName?.(),
sourceLine: sourceLocation?.getLineNumber?.(),
```

可选链不会抛错，只会得到 `undefined`。所以 surface 被构造成：

```json
{
  "context": undefined,
  "nodeName": undefined,
  "sourceLine": undefined,
  "parent": "dlist"
}
```

之后 `src/source-surfaces.ts` 看到这些 surface：

```ts
const policy = officialBlockPolicy(surface.context);
```

`officialBlockPolicy(undefined)` 进入 default，返回 `diagnostic`。于是输出：

```text
official-block-context.unknown
source-location.missing
```

我把 `projectSourceSurfaces` 的中间结果打出来，当前只得到 5 个 surface：一个真实 `dlist`，加 4 个错误的 `undefined` child。它完全没有进入 `Host`、`Port`、`Timeout`、`数据库`、`缓存中间件` 等真实 `list_item` 节点，更没有进入嵌套 `dlist`。

## 为什么 children 为空

这还牵涉第二层：`src/official-projector.ts` 当前只会把部分 context 投影成 abundant tree 节点：

- `section` -> section
- `paragraph` -> paragraph
- `listing` -> listing
- `table` -> table
- `open` -> 展开 children
- 其他有 source line 的 block -> 注册 target 后递归 children

它没有专门的 `dlist` / `list_item` 节点类型。`official-block-policy.ts` 虽然把 `dlist` 和 `list_item` 标为 `scan`，但这个 `scan` 主要用于内联 xref/anchor 扫描，不等于会生成结构树节点。更具体地说：

```ts
case "dlist":
case "list_item":
case "paragraph":
case "table":
case "verse":
    return "scan";
```

`dlist` 已经是已知 context，不该报 unknown。但由于 walker 把 dlist 条目数组错当成 block，真正进入 policy 的 child context 是 `undefined`。同时 projector 对顶层 `dlist` 没有建立 `descriptionList` / `listItem` 这类节点，所以它也不会出现在 `children[]` 里。即使先修好 walker，只要 model.ts 里没有列表节点类型，输出结构仍然不一定会出现你直觉期待的“描述列表树”；最多会少掉 undefined 警告，并且可以扫描其中的 xref/anchor。

## 样例本身还有一个独立细节

你的文件开头是：

```adoc
= 我的笔记
下面是系统的配置参数：

Host:: 127.0.0.1
```

AsciiDoc 文档标题后如果紧跟一行普通文本，并且没有空行，Asciidoctor 会把那一行当成文档头部里的 author 信息，而不是正文段落。我本地打印 document attributes，结果是：

```text
title = 我的笔记
author = 下面是系统的配置参数：
firstname = 下面是系统的配置参数：
blocks = [ ['dlist', 4] ]
```

所以第 2 行“下面是系统的配置参数：”没有进入正文 children。这不是当前 undefined 诊断的根因，但会让输出进一步显得奇怪：你以为它应该是第一个 paragraph，实际它被当成 author 了。

如果改成：

```adoc
= 我的笔记

下面是系统的配置参数：

Host:: 127.0.0.1
```

Asciidoctor 原始 AST 会多出一个第 3 行的 paragraph，HTML 也会先输出这一段正文。

## 当前最准确的判断

这次奇怪效果至少有两个来源：

第一，项目 bug：`official-block-walker.ts` 没有处理 Asciidoctor description list 的 tuple/array 子结构，导致数组被误识别成 block，产生 `context undefined` 和 source location missing。这个是主要根因。

第二，样例格式细节：标题后缺少空行，导致“下面是系统的配置参数：”被当成 author/document header，而不是正文段落。这个会影响输出树的正文内容，但不会造成那 8 条 unknown/missing 诊断。

第三，项目当前数据模型里没有显式描述列表节点类型。`model.ts` 目前有 section、paragraph、listing、table、xref、anchor、target、text、unknown 等，但没有 `descriptionList` / `listItem` / `descriptionTerm`。因此“修 walker”和“让输出呈现漂亮的描述列表结构”是两个不同层级的工作。前者是兼容官方 AST 模型；后者是扩展 abundant tree 的本体/输出结构。

## 建议修复方向

短期修复可以先只处理 walker：给 `official-block-walker.ts` 增加一个 children 归一化步骤。不要直接假设 `getBlocks()` 返回 `AsciidoctorBlock[]`，而是递归展开数组，把数组里面真正带 `getContext()` / `getNodeName()` 的对象抽出来。这样 `dlist` 下的 terms、description item、嵌套 dlist 都能成为 `OfficialBlockSurface`，unknown 诊断会消失，内联扫描也更有机会覆盖描述列表文本。

更稳妥的做法是针对 `dlist` 显式建模：识别 `[[terms], description]`，保留 term/description 的语义角色，而不是简单 flatten。因为描述列表里的 term 和 description 虽然都表现为 `list_item`，但语义完全不同；如果只是 flatten，源码范围、兄弟关系、父子关系和后续 RDF 投影都可能丢失重要信息。

中期修复应该扩展 `model.ts` 和 serializer，让输出树能表达：

```text
descriptionList
  descriptionItem
    terms[]
    description
      children[]
```

或者至少表达为通用 `list` / `listItem`，带 `listKind: 'description'`、`role: 'term' | 'description'`。如果这个工具的目标是“analysis-ready tree”，描述列表本身就不应该只是被 scan 掉，因为它承载了 key/value、术语/定义、配置项/说明等非常关键的结构语义。

测试上至少要补三类用例：

1. 简单 dlist：`Host:: 127.0.0.1`，断言没有 unknown context 诊断。
2. 嵌套 dlist：类似你这个样例，断言能走到内层 `数据库`、`连接池`、`缓存中间件`。
3. 标题后空行差异：明确记录没有空行时第 2 行是 author，有空行时才是 paragraph，避免之后误判为 parser bug。

## 最后结论

这不是 Asciidoctor 没识别描述列表，也不是 `::` / `:::` / `::::` 语法本身异常。Asciidoctor 正确生成了嵌套 `dlist` 和 `list_item`；当前奇怪输出来自本项目自写 AST walker 没有适配 description list 的数组条目模型。官方文档也提醒过：自定义遍历时不能假设所有 block 的 children 模型相同；描述列表项就是数组结构。另一个需要注意的是，样例标题后少了空行，所以“下面是系统的配置参数：”会被当成 author。

# 描述列表完整建模与测试套件设计

我先明确边界：这份内容是设计，不是补丁。我没有修改代码。当前问题不能用“遇到数组就递归拍平”解决，因为那会把 Asciidoctor 的描述列表语义抹掉，后面 source span、term/description 角色、嵌套层级、inline occurrence、target catalog、RDF 投影都会继续带病。这里应该把 description list 作为解析器的一等结构能力来建模，并给它建立一整套覆盖官方语法条件的测试套件。

我参考了三类材料：第一，项目现有设计文档，尤其是 `docs/bookshelf/books/09-asciidoc-abundant-tree-parser-spec/chapters/05-node-model.adoc` 和 `07-official-ast-and-source-surface.adoc`，它们已经规定 official AST 是结构权威，source surface 只提供原始文本证据。第二，现有代码链路：`official-block-walker.ts`、`source-surfaces.ts`、`source-interval-resolver.ts`、`official-projector.ts`、`inline-occurrence-scanner.ts`、`serializers.ts` 和 RDF heading projection。第三，官方 Asciidoctor 文档和本地 `@asciidoctor/core@3.0.4` 探针。官方 Find Blocks 文档明确说 `find_by` 用来隐藏不同 block model 的差异，并特别提醒 description list 的 item 是两个节点组成的数组；Description Lists 文档定义了 terms、description、合法 delimiter、嵌套 delimiter、混合内容；Document Header 文档解释了标题后第一空行才结束 header，因此你手写样例里第二行被当成 author 是符合官方规则的。参考链接：

- https://docs.asciidoctor.org/asciidoctor/latest/api/find-blocks/
- https://docs.asciidoctor.org/asciidoc/latest/lists/description/
- https://docs.asciidoctor.org/asciidoc/latest/document/header/

## 一、根因重新定性

当前缺陷不是“某个语法 case 漏了”，而是内部 official block traversal 对 Asciidoctor block model 的类型假设错误。当前 `walkOfficialBlocks` 只做：

```ts
(block.getBlocks?.() ?? []).map((child, index) => walkBlock(child, surface, index))
```

这个假设对普通 `section` / `open` / `paragraph` / `listing` 等场景可用，但对 `dlist` 不成立。Asciidoctor 中 `dlist.getBlocks()` 返回的是 item tuple：

```text
[
  [termItem1, termItem2, ...],
  descriptionItem
]
```

所以当前 walker 把 tuple array 当成 `AsciidoctorBlock`，自然读不到 `getContext`、`getNodeName`、`getSourceLocation`，于是产生 `context undefined` 和 `source-location.missing`。这个 bug 的直接症状是 diagnostics；更深层症状是整个描述列表结构没有进入公共 tree。即便把数组递归展开，最多能消掉 undefined warning，也不能表达“这个 list_item 是 term，那一个 list_item 是 description”。对解析器项目来说，这不够。

我本地探针确认了多个官方 AST 形状：

- 基本项：`CPU:: The brain.` 变成一个 `dlist`，其 item 是 `[[term], description]`。
- 换行描述：`CPU::\nThe brain.` 中 term 在 term 行，description item 的 source line 在下一行。
- 多术语同描述：`Hard drive::\nHard disk::\nPersistent storage.` 是一个 item，terms 数组长度为 2，共用一个 description。
- 空描述或连续 term 边界：`Term::\nNext:: Value` 会被 Asciidoctor 解释成多术语同描述，不是两个 item。这个很重要，不能用肉眼直觉设计测试。
- 嵌套：`Outer::\nInner::: Value` 里 Outer 的 description item 是一个空文本/空值 item，children 里挂 nested dlist。
- `;;` 也会触发新的嵌套层级。
- `[horizontal]` / `[qanda]` 仍然是 `dlist`，style 分别是 `horizontal` / `qanda`。
- 描述项可以包含附加块、open block、paragraph、nested dlist 等 compound content。
- term 和 description 文本里可以出现 xref/anchor，Asciidoctor 的 `getText()` 会给出 substituted HTML-like text，但 source occurrence 应该仍从源文本 line span 扫描。

因此本项目要补的是“description list 结构模型 + source recovery + projection + occurrence scanning + test oracle”，不是一个 walker 小修。

## 二、模型设计：把描述列表作为公共节点

我建议在 `src/model.ts` 增加三个公共节点类型，保持足够语义化，但不引入完整 inline CST：

```ts
type DescriptionListNode = NodeBase & {
  kind: "descriptionList";
  ids: string[];
  title?: string;
  style?: "horizontal" | "qanda" | string;
  delimiter?: string;
  metadata?: MetadataNode[];
  span?: LineSpan;
  contentSpan?: LineSpan;
  items: DescriptionListItemNode[];
};

type DescriptionListItemNode = NodeBase & {
  kind: "descriptionListItem";
  terms: DescriptionTermNode[];
  description?: DescriptionNode;
  span?: LineSpan;
};

type DescriptionTermNode = NodeBase & {
  kind: "descriptionTerm";
  text: string;
  line?: number;
  sourceSpan?: SourceSpan;
};

type DescriptionNode = NodeBase & {
  kind: "description";
  text?: string;
  line?: number;
  sourceSpan?: SourceSpan;
};
```

几点设计原则：

1. `DescriptionListNode` 是 block 级节点，和 `paragraph`、`listing`、`table` 一样出现在 `children` 里。不能只把它当 scanner 容器，因为描述列表天然承载 key/value、术语/定义、配置项/说明，是结构事实。

2. `DescriptionListItemNode` 是列表项的语义边界。它不应该复用普通 `paragraph`，也不应该只靠 `children` 表达，因为 terms 和 description 的角色关系不是普通父子关系。

3. `DescriptionTermNode` 和 `DescriptionNode` 保留 source layer 与 inline occurrence children。term 文本中的 `<<xref>>`、description 文本中的 `anchor:...[]` 都要可以挂在各自节点 children 中，或者至少进入 document-level occurrence catalog 且有正确 sourceSpan/containingSectionId。

4. `DescriptionListNode.items` 是主结构字段。为了兼容现有 serializer，也可以同时让 `children` 指向 items 或由 serializer 递归 items。更干净的做法是扩展 serializer 的 child priority，让 `items`、`terms`、`description` 以稳定顺序输出。

5. `style` 保存 official `block.getStyle()`。`horizontal` 和 `qanda` 不应变成新 kind，因为它们仍然是 description list，只是 rendering/semantic style 不同。

6. `delimiter` 建议从 source line 提取，用来记录本层 list 的 delimiter，例如 `::`、`:::`、`::::`、`;;`。官方 AST 暴露 marker 时在 JS 侧有时是 nil-ish object，不能完全依赖 `getMarker()`。source line extraction 是可接受的，但只能在 official `dlist`/`list_item` 锚点上局部读取，不允许全文件正则创建结构。

## 三、内部官方 surface 不应丢语义角色

当前 `OfficialBlockSurface` 只知道 parent/children/index。这对普通 block 够用，对 dlist 不够。我建议引入 dlist 专用 surface metadata，而不是让公共 model 直接理解 Asciidoctor tuple。

可以扩展：

```ts
type OfficialBlockSurface = {
  block: AsciidoctorBlock;
  context: string | undefined;
  nodeName: string | undefined;
  sourceLine: number | undefined;
  parent?: OfficialBlockSurface;
  children: OfficialBlockSurface[];
  indexInParent: number;
  relation?: "block-child" | "dlist-term" | "dlist-description";
  dlistItemIndex?: number;
  dlistTermIndex?: number;
};
```

但我更倾向拆一个 `official-list-model.ts`，把 Asciidoctor 的 raw tuple 转成内部安全结构：

```ts
type OfficialDescriptionListSurface = {
  list: OfficialBlockSurface;
  items: OfficialDescriptionItemSurface[];
};

type OfficialDescriptionItemSurface = {
  itemIndex: number;
  terms: OfficialBlockSurface[];
  description?: OfficialBlockSurface;
};
```

`official-block-walker` 的职责仍是“只读 official AST，不扫源码”。它需要知道 dlist tuple 是 official AST 的一部分，可以把 tuple 中真实 block surface 取出，并标记 relation。这里不是糊补丁，因为我们不是简单 flatten；我们保留了 term/description 角色、item index、term index 和 nested dlist 的父子关系。

父子关系建议这样定义：

- `dlist` 的 children 包含所有 term surfaces 和 description surfaces，保持 document order；每个 child 带 relation。
- description surface 的 children 是它自己的 attached blocks/nested lists。
- `DescriptionListNode.items` 投影时不要仅从 flattened children 反推，而应该使用 walker 保留下来的 item grouping。

这样 interval resolver、inline scanner、projector 都能访问同一个官方 block identity，不会靠 line number 猜。

## 四、source interval 设计

描述列表的 source interval 比 paragraph/listing 更复杂，因为 item 没有显式 closing delimiter，end 要从同层下一个 item、nested item、父列表边界、下一个 sibling block 推导。设计上必须分层处理：

1. `DescriptionListNode.span`：从 list metadata 起始或第一个 term line 开始，到 list 最后一个 item 的结束 line。若后面有同父级 sibling，则不能吞过 sibling 前一行。若父级是 description item，则不能吞过父 description 的 item span。

2. `DescriptionListNode.contentSpan`：从第一个 term line 到最后一个 item end line，不含 list metadata/title/attrlist。

3. term span：从 term 文本首列到 delimiter 前一列。示例 `Host:: 127.0.0.1` 中 term `Host` 的 span 是 line 4 column 1-4，delimiter 是 5-6，description text 从 delimiter 后的空格后开始。

4. description span：如果同一行有 description，则从 description text 起始列到行末；如果 description 在下一行，则从下一行非空内容开始；如果 description 仅包含 attached blocks/nested list，则 description text 可以为空，但 description node 仍存在，source line 指向 nested content 起始行或 term 下一行。

5. 多术语同描述：item span 从第一个 term line 到 description/children end；每个 term 自己有独立 span。

6. 空描述边界：官方把 `Term::\nNext:: Value` 看成多术语同描述，所以测试应断言 terms 是 `Term` 和 `Next`，description 是 `Value`，而不是两个 item。这是很容易写错的地方。

7. 嵌套 delimiter：delimiter 改变才建立 nested dlist。`:::` / `::::` / `;;` 都要覆盖。不能把 delimiter 字符数直接映射成 level，因为官方文档明确说字符数和 nesting level 没有直接相关性；每次 delimiter 变化引入新层级。

8. header 空行：样例测试必须分成两类：标题后无空行时第二行是 author，标题后有空行时第二行是 paragraph。这要成为专门 parser-input/header 测试，不混进 dlist 测试，以免测试 oracle 不清楚。

## 五、投影策略

`official-projector.ts` 需要增加 `buildDescriptionList`。处理顺序应该在 generic fallback 前：

```ts
if (blockContext === "dlist" && officialLine !== undefined) {
  return buildDescriptionList(block, officialLine, context, interval);
}
```

`buildDescriptionList` 不应直接读取 `block.getBlocks()` 生数组，而应通过 walker/source surface 中保存的 official dlist grouping。这样 projector 不需要理解 Asciidoctor tuple 的所有异常形状。

输出树示例应接近：

```text
<descriptionList style="horizontal" ids=[...]>
  items[]
    <descriptionListItem>
      terms[]
        <descriptionTerm text="Host">
      <description text="127.0.0.1">
    <descriptionListItem>
      terms[]
        <descriptionTerm text="系统总配置 (System Configuration)">
      <description text="这里定义了整个后台运行环境的基础参数。">
        children[]
          <descriptionList>
            ...
```

注意：description text 和 children 可以同时存在。比如：

```adoc
Term:: first paragraph.
+
second attached paragraph.
```

官方 description item 的 `getText()` 是 `first paragraph.`，children 里还有 paragraph。公共模型不能用 children 覆盖 text，也不能把 text 伪造成 paragraph。它应保留 description 的直接 text，同时投影 attached block children。

## 六、inline occurrence 策略

现有 scanner 已经把 `dlist` 标为 scan，并注释说 Asciidoctor 在 dlist/table 下暴露 inline substitutions 的方式特殊。完整建模后，扫描策略要更精确：

- `descriptionTerm`：扫描 term source span，只扫描 term 文本区，不扫描 delimiter。
- `description`：扫描 description text span；如果 description 有 attached paragraph/open/nested dlist，则 occurrence 由子节点产生，避免重复。
- `descriptionList`：自身不直接扫整个 span，避免重复扫 term/description/children。
- `list_item` official surface 不作为公共 node 输出时，仍应作为 source binding anchor。
- term 中 block anchor：官方要求 term anchor 必须定义在同一行 term 开头。`[[term-anchor]]Anchored Term:: Value` 应产生 anchor occurrence 和 target，term 文本可以保留 anchor 后的显示文本。
- description 中 inline anchor：`Description anchor:desc[]` 应产生 inline anchor occurrence，sourceSpan 精确到 macro。
- term 中 xref：`Term with <<xref>>:: ...` 应进入 xrefOccurrences，sourceSpan 在 term line。
- listing/literal/pass child 内容仍然不能因为挂在 description item 下而被扫描。

这里最重要的不变量是：scanner 不再对 dlist 全 span 做粗扫，因为 dlist 内包含 nested listing/pass/table 时会重复或误扫。scanner 应以投影节点或官方 child role 为边界。

## 八、等价类与边界值测试设计

### A. 基本结构等价类

A1. 同行 description：

```adoc
= Probe

CPU:: The brain.
RAM:: Memory.
```

预期：一个 `descriptionList`，两个 item。每个 item 一个 term，一个 description。无 `official-block-context.unknown`，无 `source-location.missing`。

A2. 换行 description：

```adoc
CPU::
The brain.

RAM::
Memory.
```

预期：description line 是下一行；term span 不吞 description；list item span 覆盖 term line 到 description line。

A3. 多术语同 description：

```adoc
Hard drive::
Hard disk::
Persistent storage.
```

预期：一个 item，terms 长度 2，共用 description。这个测试防止开发者按行生成两个 item。

A4. “空描述”边界：

```adoc
Term::
Next:: Value
```

预期：按官方行为是一个 item，terms 为 `Term`、`Next`，description 为 `Value`。测试名要写清楚这是 Asciidoctor contract，不是我们发明的语义。

### B. delimiter 与嵌套等价类

B1. `::` 到 `:::`：

```adoc
Outer::
Inner::: Value
Other::: More

Second:: Done
```

预期：Outer description children 中有 nested descriptionList，nested 有 Inner/Other 两项；Second 是 outer 同层第二项。

B2. `:::` 到 `::::`：覆盖更深一级。

B3. `;;` delimiter：

```adoc
Outer::
Sub;; Value
```

预期：Sub 是 nested dlist item，不是普通 paragraph。这个覆盖官方合法 delimiter 集合。

B4. delimiter 字符数不等于 level：测试不应断言 `::::` 就一定 level 4，只断言 parent-child nesting 和 delimiter 字段。

### C. compound content 等价类

C1. description 内无序列表：

```adoc
Dairy::
* Milk
* Eggs
```

预期：description children 有 `ulist` 或当前公共模型若暂不建 ulist，则至少 walker/source surface 不报警；descriptionList span 覆盖列表内容。注意现有 model 还没有 ulist 节点，如果本次不扩普通列表，测试应只验证 dlist 不坏和 diagnostics 不误报，避免 scope 膨胀。

C2. attached open block：

```adoc
Term::
+
--
Open paragraph.
--
```

预期：description children 中投影 open 的 paragraph，source span 不把 `+` 当 description text。

C3. description 中 attached paragraph：

```adoc
Term:: first paragraph.
+
second attached paragraph.
```

预期：description.text 是 `first paragraph.`，children 有 paragraph `second attached paragraph.`。

C4. description 中 listing/pass：内部 xref 不进入 occurrence。

### D. style/metadata 等价类

D1. explicit ID/title/style：

```adoc
[#terms]
.Terms
[horizontal]
CPU:: The brain.
```

预期：descriptionList.ids 包含 `terms`，title 是 `Terms`，style 是 `horizontal`，metadata 有 id/title/attrlist。

D2. qanda：

```adoc
[qanda]
What is CPU?:: The brain.
```

预期：style 是 `qanda`，kind 仍是 `descriptionList`。

D3. attrlist named attributes：

```adoc
[horizontal,labelwidth=25,itemwidth=75]
CPU:: The brain.
```

预期：metadata attrlist 保留 `style=horizontal`、`labelwidth`、`itemwidth`，public style 取 official style。

### E. inline occurrence 等价类

E1. term xref：

```adoc
See <<target>>:: Description.
```

预期：xref occurrence sourceSpan 在 term 文本区，containingSectionId 正确。

E2. description xref/anchor：

```adoc
Term:: See <<target>> and anchor:desc-anchor[].
```

预期：xref 和 anchor 都出现，不重复。

E3. term block anchor：

```adoc
[[term-anchor]]Anchored Term:: Value.
```

预期：anchor occurrence 是 block/inline scope 按现有规则确定，target catalog 有 `term-anchor`。如果现有 anchor scanner 对这种行判定为 inline，要在设计里明确是否接受；不要悄悄改 target 语义。

E4. nested listing 不扫描：

```adoc
Term::
+
----
<<not-scanned>>
----
```

预期：`<<not-scanned>>` 不在 xrefOccurrences。

### F. document header 边界

F1. 无空行：

```adoc
= Title
下面是系统的配置参数：

Host:: 127.0.0.1
```

预期：第二行是 author，不是 paragraph；body 第一块是 dlist line 4。

F2. 有空行：

```adoc
= Title

下面是系统的配置参数：

Host:: 127.0.0.1
```

预期：body 有 paragraph，再有 dlist。这个测试不是 dlist 语义测试，而是输入边界说明测试。

### G. book-entry/source map 等价类

G1. include 文件内 description list：在 book-entry logical document 中，descriptionList、terms、description 的 source.relativePath 应恢复到 include 源文件。

G2. list 跨 include 边界：如果 Asciidoctor logical source 能解析，source layer 不应伪造单一物理文件 span；如果无法安全恢复，保留结构并给 diagnostic。

这部分可以作为第二批，因为 book-entry source recovery 本身复杂，但必须纳入最终健康套件。

## 十、验收标准

这项工作完成后，我认为最低验收应是：

1. 你原始样例加上修正 header 空行后的严谨样例，都不会出现 `official-block-context.unknown` / `source-location.missing`。
2. `parseAbundantTree` 输出中有 `descriptionList`，且嵌套结构和 Asciidoctor HTML/AST 对齐。
3. 多术语、换行描述、连续 term 边界、`:::` / `::::` / `;;`、horizontal、qanda、metadata、compound content 都有测试。
4. term/description 的 xref/anchor sourceSpan 正确，不扫描 nested listing/pass/literal 内容。
5. serializer 的 pretty tree 和 JSON 都能稳定输出新增节点，不靠对象 key 的偶然顺序。
6. RDF heading projection 不因为新增 list nodes 改变 heading 数量、heading containment、previousSibling。
7. book-entry 至少有 include 文件中 dlist 的 source.relativePath 回归测试。
8. 文档 header 空行行为被单独测试并写进 fixtures 说明，避免以后把 author 行误当 parser bug。
9. 所有新增测试和现有测试通过，`pnpm typecheck`、`pnpm lint` 或项目 `pnpm check` 通过。

## 十一、我建议采用的总体方案

我推荐“官方 tuple 专用建模 + 公共 descriptionList 节点 + 分层测试”这条路线。它比简单 flatten 成普通 block 麻烦，但这是解析器项目应该做的。flatten 的主要问题是丢掉 term/description 角色，一旦公共输出没有角色，后面想做配置项抽取、知识图谱投影、RDF field predicate、动画 YAML、语义搜索都会重新猜结构。现在补全模型，成本高一点，但债务一次还清。

我不建议把 description list 暂时投影成 paragraph 或 table-like rows。description list 不是表格，它允许多 term、compound description、嵌套列表、attached blocks、horizontal/qanda style；用 rows 表达会在 compound content 上崩。也不建议为了快速通过测试只在 `officialBlockPolicy` 里忽略 undefined，因为那只是把诊断藏起来，children 仍然缺失。

最终架构应该是：

```text
@asciidoctor/core officialDocument
  -> official-block-walker
  -> official-description-list grouping
  -> source-interval-resolver
  -> official-projector builds DescriptionListNode
  -> inline scanner scans term/description ranges by role
  -> serializer/RDF/downstream regression
```

这里 official AST 仍是结构权威，source text 只提供 raw/span/delimiter/metadata 证据。所有 heuristic 都必须锚定 official block 或 official dlist item，不允许回到全文件正则扫描。
