# 对 12 号书、033 原始材料、好书笔记与 07 号书的完整对照判断

我已经按你指定的顺序完整阅读了四份材料：

1. `12-asciidoc-abundant-tree-guide.txt`，3278 行。
2. `033-raw.md`，2148 行。
3. `notes/关于书架/好书.md`，54 行。
4. `07-structured-writing-conventions.md`，844 行。

另外，因为这次本质上是在判断一件“书”这个人工制品是否对齐原始问题世界、读者动作和思想目标，我也补读了 `observation-judgment-and-action` 技能文档；因为你要求的是文本对象、语义纪律和书稿正文/设计说明的层位区分，我也使用了 `semantic-writing-discipline` 的对象语言、话语单位和必要性审查框架。

我的总判断先说清楚：**你对 12 号书的直觉是成立的，但要精确表达。12 号书不是完全没有吸收 033；它吸收了 033 的目录骨架、术语集合和一些案例方向，却没有充分吸收 033 的核心精神：让读者发生“信息观”的改变。它更像一份被切成很多小章的投影契约手册、案例库存量说明和 API/词表参考，而不是一本能够把读者从“我在写文档”带到“我在创建资源图和信息工作界面”的书。**

它的问题不是简单地“写了太多 parser / lexer / compiler”。我核查了 12 号书全文，`lexer`、`compiler`、中文“词法”“编译器”并不是高频主体；`parser` 也只在少量位置出现，例如 N3 Parser、logical document 被 parser 解析。真正造成你感到“怎么全是解析器、编译器、Lex、Parser 细节”的原因，是另一种更深的现象：**书稿的叙述重心大量落在投影内部契约、API 表面、RDF 词表、字段规则、source span、selector binding、edge evidence、raw value object、SHACL/Oxigraph/RDF/JS 等工具链对象上，而不是落在读者如何改变自己对信息、资源、书写、文件、图和下游消费的理解上。**也就是说，问题不是某几个词太多，而是技术契约层夺走了思想主线的位置。

## 一、033 原始材料真正要的是什么

033 不是单纯要求“写一本工具教程”。它提出的对象更大：**一套以书稿作为信息建模工作界面的思想、约定和工具链。**

033 的核心断言可以压缩成这样：

> 人类按照可读书稿的方式写标题、字段、引用和 payload；工具链把这些表面投影成 RDF/TTL；TS/JS、SPARQL、SHACL、图数据库、RAG、多模态模型和 code agent 能在这个投影上查询、校验、转换、回源和维护。于是写文章/写书不再只是写文档，而是在创建可读、可查、可验证、可回源、可由程序和 agent 共同消费的资源图。

033 里面反复出现的不是“解释 API”，而是几个思想转换：

第一，**标题就是资源节点**。这不是教学比喻，而是本体转换。传统上，人容易把“一个文件”当作资源节点：图片是文件、PDF 是文件、配置是文件、剧本是文件、笔记是文件。但在这套系统中，一个标题可以成为资源节点。标题下面可以挂正文、字段、图片链接、payload、xref、索引词、回源坐标。资源节点从文件系统对象转移到书面结构对象。

第二，**书稿表面是一种信息工作界面**。AsciiDoc 不是被当成一个语法玩具，而是因为它本来就是严肃出版和技术写作的媒介：标题、章节、交叉引用、属性、描述列表、include、frontmatter/body/backmatter 都已经存在。工具链在这个人类可读表面上建立投影，让写作动作同时成为结构化录入动作。

第三，**投影不是业务本体**。投影层保存结构事实：heading、field、xref、raw、source coordinate、edge evidence。业务语义由下游 role/rel/field/payload schema、TS/JS policy、SHACL、外部 TTL 或图数据库 adapter 解释。033 要求读者理解“结构层”和“业务建模层”的分层，而不是把投影器写成懂冷链、懂菜谱、懂图片、懂 K8S 的智能业务引擎。

第四，**这套系统降低的是偶然复杂度，不是本质复杂度**。医疗、金融、图片资产、K8S、剧本、PDF 溯源各自仍然复杂。但书稿表面、纯文本、Git、rg、apply_patch、SPARQL、TS/JS、source coordinate 共同降低了录入、维护、查询、回源和 agent 协作的环境复杂度。这是 033 中“环境邀请”“人因工程”“可供性”的思想核心。

第五，**读者路径应该由浅入深，从纯结构走向开枝散叶的行业案例**。033 明确说：先讲最基础的写法和投影，让读者看到“这么写就能投影成这样的 TTL，这样写 JS/SPARQL 就能查”；然后讲字段、边、payload、多文件书、跨书；再进入领域建模、外部 TTL、Neo4j、RAG、多模态资产、K8S、剧本等案例。越上层越纯结构，越下层越接近具体行业本体。

第六，**正文必须是对象语言，不是作者说明书**。033 后半段最强烈批评的就是“本书不教 X”“未来可以”“至少一种”“下一步先做骨架”这类元层次混淆。设计说明可以给你看，书稿正文不能这么写。书稿正文应该直接呈现对象、规则、例子、查询、代码、结果和回源证据。

所以 033 期待的 12 号书，不是“把所有内部概念列完”，而是：**让读者进入一个新世界，意识到写作可以创建图，标题可以成为资源节点，文本可以成为全模态信息资产的统一索引面，TTL/TS/JS/SPARQL 是这种书写约定的可消费投影。**

## 二、好书笔记给出的约束

`好书.md` 很短，但它给了三个层级的判断标准。

第一层是思想与逻辑：一本好书必须有核心论点，经得起检视阅读、分析阅读和主题阅读。它不是信息堆叠，而是一个思想金字塔。12 号书现在有很多局部对象，但中心论点的持续支配力不足。读者看得到“heading node”“raw value object”“xref edge evidence”，但不一定会被带到“信息可以用书稿方式进入资源图”的认知转变。

第二层是文笔与风格：省略赘词、肯定表达、清晰表达。12 号书很多句子本身是干净的，甚至比上一轮 033 中被批评的设计说明更少废话；但它出现了另一种问题：**句子都很短，却像术语卡片，彼此之间缺少足够的概念推进。**这不是冗长，而是“压缩成 reference 后丢失思想呼吸”。寸土寸金不是把每段写短，而是每个字都改变读者判断。12 号书不少段落只是在登记事实。

第三层是书籍形态：front matter、body matter、back matter、术语表、参考文献、索引等是严肃书籍的稳定结构。12 号书表面上做了这些，但在你给的 `.txt` 聚合产物里，前 300 多行先是扫描格式说明和目录树，接着是 backmatter 附录，再到 frontmatter，再到正文。这作为“手动聚合的阅读文件”严重破坏了书籍的第一阅读路径。就算源 `book.adoc` 顺序是正确的，这份 `.txt` 作为你让我精读的书本聚合物，也不是一本书的阅读表面，而是一个源码包 dump。它让读者先看到构建物、附录、API、术语表，再看到引言，第一印象已经从“进入思想”变成“读工程归档”。

## 三、07 号书为什么虽然短，却更接近“书”

07 号书只有 844 行，但它的价值在于：它用很少的东西完成了一个闭合示范。

它先给源文本与投影：一个 AsciiDoc 片段，紧接着给 Turtle 片段，再解释标题、role、xref、rel 如何投影。它不是抽象地说“工具支持投影”，而是让读者看到一个写法和一个结构结果之间的对应。

它再讲默认语义、stable ID、role、rel、字段、索引和术语表。它并不试图穷尽所有内部机制，而是围绕“结构化书写约定”这个对象展开。附录 A 是速查，附录 B 是决策树。决策树不是装饰，而是给作者在写标题、ID、role、xref、field、编号、index term 时做判断。

更重要的是，07 号书自己就是它讲的东西的实例：book-entry、frontmatter、parts、backmatter、glossary、bibliography、index 都在它自己身上出现。它短，但有对象、有示例、有速查、有决策树、有书籍形态。

07 号书也不是完美的。它里面仍然有一些“希望你能通过本章节……”之类的教学口吻，也有个别句子像给读者解释作者意图。但它的结构力量比 12 号书当前聚合物更清楚：它没有把自己拆成几十个微型术语条目，它先让读者看到一个完整的写法-投影关系。

## 四、12 号书实际吸收了哪些 033 的东西

公平地说，12 号书不是完全偏离。它已经吸收了很多 033 中的“名义对象”。比如：

- 标题作为资源节点。
- 第一张可查询图。
- 源文档、AbundantDocument、Projection。
- heading slice、containsDirectly、childOrder、documentOrder。
- stable ID、role、attrlist、description list、hmeta。
- xref、rel、edge evidence、selector binding。
- complex property、raw value object、heading payload、edge payload。
- SPARQL、SHACL、RDF/JS、Oxigraph、source-aware report。
- book-entry、source set、logical document、line origin。
- 领域建模：role 词表、rel 词表、field/payload schema、hierarchy policy、business graph。
- 官方案例库：basic RDF、cold-chain payload、recipe KG、cold-chain operations、book workspace、cross-book、multimodal asset、PDF/Word/RAG、K8S、screenplay/game、external TTL/Neo4j。

这些对象确实来自 033 第二轮正式说明。12 号书基本按照那份章节计划落成了源文件目录。

但问题也正出在这里：**它像是把 033 第二轮说明的“章节安排”机械铺开了，却没有把 033 第一手思想材料里那种强烈的世界观转换写进每一章。**它保留了结果列表，丢失了推进逻辑。

## 五、12 号书的主要偏离

### 1. 聚合物不是书，第一阅读路径已经损坏

你让我读的 `12-asciidoc-abundant-tree-guide.txt` 开头是：`<document>`、`<format_guide>`、summary stats、directory tree、unified diff 文件头。这对 code agent 做完整扫描有用，但对“书”是灾难。它不是读者入口，而是源码包归档。

尤其荒谬的是，附录 A、B、C、D、E、F、参考文献、术语表、索引在聚合顺序里出现在摘要、引言、前言之前。一本书的读者还没进入对象，就先被投喂速查表、词表和 API reference。这会让读者把它理解成一个工具包说明，而不是一个思想入口。

这件事必须区分：源 `book.adoc` 的 include 顺序本身看起来是 frontmatter -> body -> backmatter；但你这份“手动聚合的书本”作为读物，明显不是书的阅读投影。**如果最终交给读者的表面长得像这个 txt，那它不是书。**如果这个 txt 只是给 agent 扫描源码，那它不能被当成“书本现状”来判断读者体验，只能作为源码快照判断内容质量。

### 2. 它把“概念树”写成了“对象清单”

12 号书有九部，章节非常多，但很多章只有二三十行。每章定义一个对象，给一段 AsciiDoc 或 Turtle，然后一两句说明。这种写法适合 reference，但不适合承担 033 要的思想转变。

比如“标题作为资源节点”这一章有图片资产例子，最后也写了“文件是字节容器；标题节点是书稿中的资源容器”。这是很好的句子，但展开太少。033 里这部分是最震撼的思想之一：从 Eagle/Billfish/Pixcall 到多模态模型读图、写回字段/payload、纯文本 agent 可 patch、图查询统一检索、环境偶然复杂度下降。12 号书只留下一个图片例子和几句定义，没有把这个例子变成读者信息观的改变。

也就是说，它有“资源节点”这个词，但没有充分制造“原来资源节点不必是文件，而可以是标题；原来我写书稿就是在组织全模态信息资产”的顿悟。

### 3. 它过早进入契约细节，读者还没有完成世界观转换

12 号书第一部之后，很快进入 heading slice、metadataStartLine、contentStartLine、childOrder、documentOrder、local target ownership、selector binding、reifier、raw value object 等精细契约。这些都不是不该写；它们是需要的。但问题是：读者还没被建立成“我要用书稿进行信息建模”的人，就被拉去核对投影字段。

033 期望的路径是：先让读者看到“我这么写，就能投影成 TTL；我写 JS/SPARQL，就能查；我能回到源文件；这很强”。然后再逐步解释为什么需要 heading slice、edge evidence、selector binding、raw opaque。12 号书现在则像：第一章给闭环，第二章给资源节点，然后马上开始 reference 化拆解。第一章的火还没烧起来，后面就进入规约表。

### 4. 技术细节不是错，错在没有被读者动作授权

`AbundantDocument`、CLI、Library API、RDF/JS、Oxigraph、SHACL、source span、line origin 都是必要对象。但它们进入正文时必须回答：读者现在要完成什么动作？这个对象如何改变读者判断？它如何服务“书稿作为信息工作界面”？

12 号书很多地方是“对象存在，所以定义它”。例如 `Source Document、AbundantDocument 与 Projection` 章主要解释 API 返回对象和 projection 表面；它对开发者有用，但对一般读者来说，它没有足够地连接到“同一份源文档在人的阅读表面、解析对象和查询图之间如何同构”。读者看到的是 object model，不是“信息拓扑的多表面等价”。

你说“它们只是结构拓扑上的变化，信息量等价”，这个点在 12 号书里没有被写成核心思想。它展示了源文档和 Turtle，但没有持续强调：**AsciiDoc 源表面、RDF TTL 表面、TS/JS object model、JSON report、Mermaid view 是同一个信息结构在不同消费者面前的投影。**这才是哲学层面的东西。

### 5. 案例库像库存说明，不像官方案例章节

第九部每个案例基本是 15 行：领域对象、source/projection/model/reports/views、几句说明、读者动作。这是案例清单，不是案例章节。

033 要的官方案例是“一个源书稿、一份建模约定、一份投影 TTL、一份 TS/JS 消费脚本、查询/校验、输出视图、回源证据”的闭环。12 号书确实建了目录，也列了这些产物，但正文没有把案例带读者走完。读者不会从 `Multimodal Asset Catalog` 的 15 行里真的感受到多模态资产如何被书稿化；不会从 `PDF / Word / RAG Provenance Index` 的 15 行里真的看到外部复杂文件如何进入统一图索引；不会从 `K8S Microservice Configuration Graph` 的 15 行里真的理解配置、生成物、依赖查询、漂移检查如何同构。

这就是“有案例名，没有案例”。至少在当前书稿正文层面是这样。

### 6. 12 号书没有充分呈现“信息”的哲学对象

你这次问题里一直强调 information、异构数据、全模态、资源节点、信息处理、哲学看法改变。033 里这些都很强：图片、PDF、Word、RAG、K8S、剧本、医疗金融中医药、生物、个人资料、agent、纯文本、图查询、适配器、反向导出、双向同步。

12 号书里这些词和案例方向存在，但大多压在第八、第九部，而且写得很短。它没有在引言和第一部持续建立“信息是什么”这个对象：

- 信息不是只存在于文件里。
- 信息可以被书稿表面组织。
- 标题可以成为信息资源的边界。
- 字段、xref、payload 是信息进入结构图的表面。
- TTL 是同一信息拓扑的标准图投影。
- TS/JS 是进一步操作、转换、生成、适配的行动层。
- source coordinate 保留回源，使图不是漂浮的抽象知识库。
- 多模态和异构数据通过链接、payload、selector、外部 URI、adapter 接进统一查询面。

这些应该是全书的脊柱。12 号书现在更像先讲工具契约，再在后面列“也可以做这些行业”。顺序上看似对，精神上不够。

### 7. 它太像“把设计说明转写成正文”

033 第二轮说明明确区分三层：书稿正文、给你的设计说明、执行计划。12 号书比第一轮错误好很多，基本没有大量“本书不……”式否定排除，也没有一直说“未来”。但是它仍然保留了设计说明的影子：每一部 partintro 都在“本部定义 X”；很多章节像“主对象定义卡”；案例契约像验收清单。

严格说，这些句子未必错，但它们让书稿表面显得像规约文档，而不是一本能引导读者思想改变的书。**书可以有 reference 层，但正文主线不能全部 reference 化。**

### 8. 代码和 example 的关系仍然没有达到 033 的要求

你问“为什么代码以及 example 的样例是分开的？它不应该在一本书里面吗？”

12 号书现在的结构是：正文讲概念，cases 目录放源、projection、model、reports、views，正文第九部再用清单引用这些案例。这比散落样例好，但还没有达到“书内完整案例”的形态。

更好的关系应该是：

- 每一章的正文先有最小源表面。
- 紧接着给实际投影片段或报告片段。
- 紧接着给可运行 TS/JS 代码。
- 紧接着给输出。
- 紧接着解释这个输出如何回源。
- 完整案例目录作为可复制工程，正文引用其文件路径，但读者不需要跳出去才能理解闭环。

现在 12 号书的正文代码有一些，但很多案例仍只是目录说明。读者会知道“那里有代码”，但没有在书的阅读流中被带着跑完。

## 六、关于“使用者需要知道这些吗？”

答案要分读者。

普通 AsciiDoc 作者、知识库维护者、领域建模者、AI agent 操作者，不需要先知道 parser、object model、RDF 1.2 reifier、Oxigraph、SHACL 的细节。他们第一需要的是：

- 我写一个标题，会发生什么？
- 我给标题加字段，会发生什么？
- 我写 xref，会发生什么？
- 我挂 payload，会发生什么？
- 我如何查它？
- 我如何回到源文件？
- 我如何把图片、PDF、配置、剧本、业务规则放进这个结构？
- 我如何用 TS/JS 继续操作？

TS/JS 开发者、RDF/KG 工程师需要更细的契约，但他们也不应该在没有对象动机之前被塞进词表细节。优秀的书应该让不同读者沿同一主线进入，再在需要时分流到 reference。

所以不是“不写技术细节”，而是：**技术细节必须在读者动作之后出现，并被读者动作授权。**

例如：

- 先写“我想从查询结果回到源文件”。然后 `relativePath`、`headingLine`、`startLine`、`endLine` 有存在理由。
- 先写“我想知道这条业务边来自源文档哪一个 xref”。然后 `xref edge evidence`、`raw`、`startColumn`、`rdf:reifies` 有存在理由。
- 先写“我想把 JSON/YAML 作为复杂配置挂到标题或边上，但投影器不解释业务字段”。然后 `raw value object`、`format`、`field predicate`、schema consumer 有存在理由。
- 先写“多文件书稿要合成整体结构，但修改时要回到原章节文件”。然后 `logical document`、`line origin`、`source set` 有存在理由。

如果反过来先讲这些对象，读者会觉得自己在读解析器内部文档。

## 七、12 号书应该回到什么形态

我认为 12 号书应该重构为“双层书籍”：正文主线承担思想转变和读者动作，附录/reference 承担完整契约。

正文主线应该像这样推进：

第一部：**写下标题，就是创建资源节点**。用一个极小例子让读者看到源文档、TTL、SPARQL、TS/JS 输出、source line。这里不要急着拆所有字段，重点是让读者第一次感到“写作动作变成图结构”。

第二部：**资源节点如何拥有身份、字段和边**。讲 stable ID、role、attrlist、description list、hmeta、xref、rel。每个写法都必须有源表面、投影、查询、回源。不要只讲语法。

第三部：**复杂信息如何进入书稿资源图**。讲 payload/raw value object。核心不是“source value block 的绑定规则”，而是“JSON/YAML/外部定位/模型输出等复杂结构如何被挂到一个可读资源节点或关系边上，并由 TS/JS schema 消费”。

第四部：**同一信息结构的多个投影**。集中讲 TTL、JSON-LD、RDF/JS、SPARQL、SHACL、source-aware report、Mermaid/business graph。主题是“信息拓扑同构映射”，不是工具名罗列。

第五部：**多文件书与长期知识人工制品**。吸收 07 号书的结构：frontmatter、parts、chapters、backmatter、glossary、bibliography、index、source-order notation、xref audit。这里要把“书本身就是可投影对象”写出来。

第六部：**领域建模：从结构图到业务图**。讲 role/rel/field/payload schema、hierarchy policy、business graph generation。这里明确投影器不做业务解释，但不要用否定式写法；正面写：投影层保存结构事实，领域层声明解释政策。

第七部：**官方案例库**。每个案例不能只是 15 行清单，而要成为可阅读案例：源书稿片段、建模约定、TTL 片段、TS/JS consumer、报告、视图、回源。案例顺序从纯结构到多模态/外部文档/K8S/叙事/外部图谱。

第八部或后置参考：**完整契约与速查**。这里放 CLI/API、RDF 词表、SHACL 模板、决策树、字段表面速查。技术细节不是删掉，而是放到读者已经知道为什么需要它们的位置。

## 十一、我会如何改写它的基本原则

7. 书稿正文只写对象语言，不写给作者自己的设计说明。

# 12 号书整书修订对齐方案

我先把刚才那条错误纠正清楚：`12-asciidoc-abundant-tree-guide.txt` 是给 agent 扫描的聚合物，不是读者最终阅读表面。它开头有扫描格式、目录树、unified diff 边界，这不是书稿自己的罪。这个判断我撤回。后续修订只针对 `docs/bookshelf/books/12-asciidoc-abundant-tree-guide/` 里的真实书稿、章节正文、案例材料、附录和生成脚本，不再把扫描包装当成书籍顺序问题。

## 一、整书对象重新确定

这本书的对象不是 `asciidoc-abundant-tree` 的 API 手册，不是 RDF 教材，不是 AsciiDoc 写法大全，也不是案例目录。

这本书的对象是：**用 AsciiDoc 书稿作为信息建模、资源组织、图投影、代码消费和回源维护的工作界面。**

这个对象包含八个不可缺的构成性条件：

1. **书稿表面**：人类仍然在写文章、写书、写资料，不被迫直接写三元组。
2. **资源节点**：标题不是装饰标题，而是可查询、可引用、可回源、可挂载信息的资源节点。
3. **结构约定**：role、field、xref、rel、payload、层级、stable ID 都是书稿表面的结构约定。
4. **标准投影**：这些约定投影为 RDF 1.2 / TTL / JSON-LD，让结构进入 W3C 图生态。
5. **代码消费**：TS/JS 程序读取投影，生成报告、业务图、视图、校验结果、adapter 输入。
6. **回源闭环**：查询结果、校验结果、业务报告必须能回到源文件、标题、行号和原始片段。
7. **开放建模**：投影层只保存结构事实；业务语义由领域 role/rel/field/payload schema 和下游 policy 承担。
8. **异构与全模态接入**：图片、PDF、Word、RAG chunk、K8S YAML、剧本、外部 TTL、Neo4j、个人资料都能通过标题节点、payload、xref、外部 locator 和 adapter 接入统一查询面。

这八个条件决定全书如何组织。每章必须服务其中一个条件，不能只因为某个术语存在就占一章。

## 二、当前书稿的根本问题

当前书稿的问题有四类。

### 1. 章节被 reference 化

当前 `parts/020` 到 `parts/060` 很多章节只有 20 到 40 行，形态是：定义一句、给一段源表面、给一段 TTL、补一两句边界。这种形态适合附录或 reference，不适合作为正文主线。

书稿因此变成“对象卡片集合”。读者会知道 heading node、heading slice、containsDirectly、addressLabel、role、edge evidence、raw value object 等对象存在，但读者不会被带着完成认知转换。

正文主线必须先让读者看到一件事：**我这么写，就能产生这样的图；我用代码能这样查；我能回到源文档；我能把自己的信息资产放进这个结构。**术语和契约要跟在这个动作后面。

### 2. “标题是资源节点”没有成为全书发动机

当前有 `020-heading-as-resource-node.adoc`，也有图片资产例子，但只写了 34 行。033 里最强的东西正是这里：从文件资源转向标题资源，从孤立图片/PDF/配置转向书稿中的资源节点，从人类写字转向图结构录入，从纯文本环境转向 agent 低摩擦维护。

这章必须成为第一部的核心章，不能只是一个短定义。它要把读者带过三个观念变化：

- 文件仍然存在，但资源边界不再只能由文件决定。
- 标题节点是可读资源容器，能挂字段、图片、payload、xref、回源坐标。
- 进入标题节点以后，异构信息就进入统一查询面和下游消费面。

### 3. 案例库只是库存说明

第九部现在每个案例 15 行左右，本质是案例目录说明：source/projection/model/reports/views 分别是什么，读者动作是什么。这是库存，不是案例章节。

033 要的是官方案例库。案例必须让读者实际看见：源书稿如何写，TTL 如何投影，TS/JS 如何消费，报告如何回源，视图如何生成，业务解释政策如何声明。当前案例目录可以保留作为工程资产，但正文必须扩写成真正的案例。

### 4. 技术细节缺少读者动作授权

并不是 heading slice、line origin、RDF reifier、selector binding、Oxigraph、SHACL 不该写。它们应该写。但每个技术对象必须由一个读者动作授权。

例如：

- 读者要从查询结果改源文件，所以需要 source coordinate。
- 读者要审计一条关系来自哪一个 xref，所以需要 xref edge evidence 和 reifier。
- 读者要让 JSON/YAML 保持业务解释权在下游，所以需要 raw value object。
- 读者要把多文件书当一棵逻辑树查询，但修改时回到原文件，所以需要 logical document 和 line origin。

当前书稿常常先介绍技术对象，再补一句用途。修订后要反过来：先出现问题和动作，再出现对象。

## 三、重修后的全书结构

我不建议保留当前九部的原样顺序。大方向可以继承，但要重排主线和章节颗粒度。

我会改成八部正文加后置参考。

### 第一部：书稿创建资源图

职责：建立世界观和第一闭环。读者从第一部就必须感到“这不是写文档，这是创建可查询资源图”。

保留并重写：

- `010-first-queryable-graph.adoc`
- `020-heading-as-resource-node.adoc`
- `030-source-document-abundant-document-projection.adoc`
- `040-reading-unit-query-unit.adoc`

新增或改写重点：

1. **第一张可查询图**：保留现在的配送策略例子，但增强 TS/JS 运行路径。源文件、运行命令、生成 TTL、SPARQL 查询、输出表、回源行号必须连起来。当前第一章已有骨架，可以扩写而不是推倒。

这部不讲过多边界，不讲完整词表。目标是把读者拉进世界。

### 第二部：资源节点的表面约定

职责：讲标题如何拥有地址、身份、字段、正文、层级和维护边界。

当前 `020-heading-structure` 和 `030-identity-and-fields` 要合并重排。现在拆得太碎，读者读起来像词典。重修后按动作组织：

1. **创建节点**：heading node、headingLevel、headline、document title。合并当前 `010-heading-node`。
2. **切出资源范围**：heading slice、raw、自身切片与子树。合并当前 `020-heading-slice` 与第一部子树内容的 reference 部分。
3. **组织资源树**：containsDirectly、childOrder、documentOrder。合并当前 `030-direct-containment` 与 `040-local-and-global-order`。
4. **命名和寻址**：label space、stable ID、generated label、headline。合并当前 `010-label-space` 与 `020-stable-id`。
5. **标记身份**：role。保留当前 `030-role-identity`，但加入受控词表和读者动作。
6. **添加字段**：attrlist、description list、hmeta、field placement 合并成一章，不再四个短章分散。字段落位策略要成为主线：短字段、长字段、句内字段、复杂字段分别解决什么阅读和消费动作。
7. **本地 target 归属**：保留当前 `050-local-target-ownership`，但移动到地址和引用之间，因为它是 xref 和 payload 共同依赖的寻址事实。

这一部的核心不是“有哪些字段规则”，而是：**一个标题节点如何被找到、分类、描述和维护。**

### 第三部：引用创建关系边

职责：让读者理解 xref 不只是跳转链接，而是资源节点之间的边。

当前 `040-xref-and-relations` 保留，但要扩写、合并、调序：

1. **xref 创建边**：保留当前 `010-xref-relation-edge`，加强源 heading、target heading、relation triple 的图形说明。

## 七、写作风格约束

## 八、我自己的执行注意事项

### 1. 不为现状辩护

我不能因为现有文件树完整、对象名齐全、案例目录齐全，就替它找理由。判断标准是读者是否完成认知变化、动作是否闭环、案例是否可运行、书稿是否自包含。

后续只改真实书稿目录。扫描聚合物只作为 agent 读取材料，不再把它的排序作为书籍问题。

### 3. 不打小补丁

如果一章结构上不承担正文主线，就合并、移动、降级或重写。不能只在段首加几句“哲学”来装饰。

### 4. 每个设计点要有授权

新增章节、移动章节、扩写案例、保留技术细节，都必须能回答：服务哪个读者动作？改变哪个判断？成本是什么？验证方式是什么？

033 里真正重要的不是某个目录，而是信息观转换。我每改一部都要检查：这一部是否让读者更接近“书稿是信息建模工作界面”？如果没有，就不合格。

### 6. 保留工程真实性

这不是纯文学改写。所有 TS/JS、TTL、reports、views、case generator 都要和项目实际能力对齐。不能写出跑不通的示例。

### 7. 不把 case 写成广告

多模态、RAG、K8S、剧本这些案例不能只说“适合”。要给源书稿、字段、payload、关系、代码、输出。否则就是空话。

### 8. 不让 reference 抢正文

完整契约很重要，但正文是读者路径。reference 进附录，正文保留必要契约和动作闭环。

### 9. 每次改动后检查交叉引用

这是 AsciiDoc 书，不是散文文件。改文件、改标题、改 stable ID 后要检查 xref、索引、术语表、include 顺序。

### 10. 生成物不手写乱改

大 JSON-LD 和 TTL 应由工具生成或有明确来源。正文摘片段可以手写/压缩，但案例产物要同步验证。
