# 标题描述列表元数据挂载机制说明

下面这份说明把我们前面分散讨论的内容整理成一个完整、可交给别人阅读的需求描述。它包含当前代码现状、用户希望得到的作者体验、AST 层面的机制定义、成功与失败条件、数据模型建议、实现位置、测试与验收标准。阅读这份说明的人不需要知道我们前面聊天里的所有来回，也能理解这项功能为什么要做、应该怎么做、边界在哪里。

## 一、背景：当前项目是什么

`asciidoc-abundant-tree` 是一个源感知 AsciiDoc 解析器项目。它不是为了替代 Asciidoctor，而是把 Asciidoctor 作为官方语义解析层，再把解析结果投影成项目自己的 `AbundantDocument` 对象模型。这个对象模型会保留标题、段落、列表、表格、代码块、源文本位置、xref、anchor、target catalog、RDF 1.2 heading projection 等信息，供后续静态分析、知识图谱投影、编辑工具、文档检查工具使用。

当前项目已经有两类和“标题元数据”有关的机制。

第一类是 AsciiDoc 官方风格的标题前 metadata，也就是写在标题前面的 attrlist、id、block title、anchor 等。例如：

```adoc
[apple="red"]
== 大苹果
```

当前解析器会把 `[apple="red"]` 识别为 `SectionNode.metadata` 里的 `MetadataNode`。如果输出 RDF 1.2 heading projection，这些 attrlist 字段也可以作为 heading 的 direct field predicate 投影出去。

第二类是当前已经完成的一等 description list AST 建模。项目现在已经能够把描述列表解析成：

```ts
DescriptionListNode
  items: DescriptionListItemNode[]
    terms: DescriptionTermNode[]
    description?: DescriptionNode
```

也就是说，当前代码已经不再把 description list 当成普通 paragraph，也不是靠文本正则去猜 `::`。它已经从 Asciidoctor official AST 中正确识别 dlist tuple 模型，并把 term、description、嵌套 description list、source span、inline occurrence 等信息投影到项目自己的 AST 中。

这次需求不是重新实现 description list 解析；当前 description list 解析能力已经存在。这次需求是在现有 AST 之上新增一层“标题描述列表元数据挂载机制”。

## 二、当前痛点：标题前 attrlist 不适合自然书写多行字符串

AsciiDoc 官方标题前 attrlist 很适合短字段，例如：

```adoc
[type=fruit, color=red, weight=300g]
== 大苹果
```

但它不适合自然书写长文本和多行字符串。因为 attrlist 是一行内的属性语法，长文本如果要放进去，通常需要绕路。例如：

```adoc
:my-multiline-desc: 这是第一行描述内容。 + \
这是第二行描述内容。 + \
这是第三行，内容非常多...

[apple="{my-multiline-desc}"]
== 大苹果
```

这种写法在官方语法层面是可行的，但从作者体验看很绕。作者的真实意图只是：“我想给这个标题写一段元信息，这段元信息可能很长，可能有多行。”但是 attrlist 迫使作者用变量、continuation、替换语法或字面 `\n` 去间接表达。

我们讨论过的 `描述列表3.adoc` 就体现了这个问题：它展示了标题前 attrlist 可以通过一行内的 `\n` 字面形式承载多行语义，但这种方式不自然，不适合作为长期推荐的作者写法。

换句话说，问题不是“标题 metadata 不能承载多行字符串”。从数据模型和下游消费角度，metadata value 本质就是字符串，而字符串当然可以包含真实换行。真正的问题是：官方 attrlist 的源文件写法不方便自然表达多行字符串。

## 三、期望体验：用标题下的描述列表自然声明标题元数据

这次新增机制的目标，是让作者可以在标题下面直接写 description list，用它作为这个标题的 metadata source。

例如，作者希望写：

```adoc
== 大苹果

类型:: 水果
颜色:: 红色
描述::
这是一个极大且红润的苹果。
它的表面带有清晨的露水。
非常适合用来制作节日的苹果派。
价格:: 5.99
```

作者的心理模型是：

- `类型` 是这个标题的一个元数据字段，值是 `水果`。
- `颜色` 是这个标题的一个元数据字段，值是 `红色`。
- `描述` 是这个标题的一个元数据字段，值是一个真实多行字符串。
- `价格` 是这个标题的一个元数据字段，值是 `5.99`。

解析器应该在 AST 后处理阶段把这个标题下面的第一个连续、扁平 description list 提升为 section 的 metadata，而不是把它继续当作普通正文内容。

最终，项目自己的 AST 中应该能得到类似：

```ts
section.descriptionMetadata = {
  fields: {
    类型: "水果",
    颜色: "红色",
    描述: "这是一个极大且红润的苹果。\n它的表面带有清晨的露水。\n非常适合用来制作节日的苹果派。",
    价格: "5.99",
  },
  entries: [...]
}
```

这里 TypeScript 例子里的 `\n` 表示真实换行字符。它不是两个字面字符，也不是要求作者在源文件里写 `\n`。作者在源文件中可以直接换行写多行文本，AST 中得到的就是一个包含真实换行的字符串。

## 四、核心概念：它不是官方 attrlist，而是项目 AST 层的语义提升

这项功能必须被理解为项目自己的 AST 后处理约定，而不是 AsciiDoc 官方语法改造。

Asciidoctor 官方层看到的是普通 description list。它负责把源文件：

```adoc
host::
127.0.0.1
苹果
banana:: 5个
```

解析成 official AST 中的 dlist/list_item 结构。

`asciidoc-abundant-tree` 当前已经能把它投影成：

```text
<descriptionList>
  <descriptionListItem>
    terms[]
      <descriptionTerm text="host">
    <description>
      text:
        127.0.0.1
        苹果
  <descriptionListItem>
    terms[]
      <descriptionTerm text="banana">
    <description text="5个">
```

新增机制要做的是：当这个 `descriptionList` 位于某个标题的 direct children 起点，并满足扁平条件时，把它提升为该标题的 `descriptionMetadata`。

因此，这不是“把 description list 转写成 attrlist”。也不应该伪造 `MetadataNode(metadataKind: "attrlist")`。标题前 attrlist 和标题下 description list 是两种不同的 source surface。它们可以在下游查询层合流为 heading direct fields，但在 AST 模型里应该保留来源差异。

正式命名可以采用：

- 机制名：标题描述列表元数据挂载机制。
- 字段名：`descriptionMetadata`。
- 节点名：`HeadingDescriptionMetadataNode` 或 `DescriptionMetadataNode`。

## 五、AST 层面的判定规则

这个机制必须完全基于现有 AST 判断，不回到源文本正则扫描。

### 1. 作用对象

只处理 `SectionNode`。每一个 section 独立判断。

文档 title 暂不参与。父标题也不读取子标题下面的列表。子标题有自己的 children，自己的 metadata 挂载独立完成。

### 2. direct children 原则

只看当前 section 的 direct children。

例如：

```adoc
== Parent

=== Child

key:: value
```

`key:: value` 只属于 `Child`，不属于 `Parent`。因为在 AST 中它是 Child section 的 direct child，不是 Parent section 的 direct child。

### 3. 起点原则

只有当 `section.children[0]` 是 `descriptionList` 时，才存在可挂载候选。

如果标题下面第一个 AST child 是 paragraph、listing、table、section、open block 或任何非 descriptionList 节点，则这个 section 不挂载 description list metadata。即使后面出现 descriptionList，也不参与。

例如：

```adoc
== 标题

这里先有一段正文。

key:: value
```

这里不挂载。`key:: value` 保持普通 descriptionList 内容。

### 4. 空行不影响

标题和 descriptionList 之间可以有任意数量空行。空行不是 AST child，因此不会影响判断。

例如：

```adoc
== 标题



key:: value
```

如果 `key:: value` 是 section 的第一个 AST child，那么仍然符合候选起点。

### 5. 第一个连续 descriptionList run

候选不是“任意位置的第一个 descriptionList”，而是从 children 起点开始连续出现的 descriptionList run。

例如：

```text
children = [descriptionList, descriptionList, paragraph]
```

前两个 descriptionList 同属第一个连续 run，可以一起作为候选。

例如：

```text
children = [descriptionList, paragraph, descriptionList]
```

只有第一个 descriptionList 属于候选。后面的 descriptionList 被 paragraph 断开，不参与 metadata 挂载。

### 6. 成功后吸收，失败后保留

如果候选 run 符合所有条件，就把它吸收到 section 的 `descriptionMetadata` 中，并从 `section.children` 中移除。这样避免同一事实既作为 metadata 出现，又作为正文 descriptionList 出现。

如果候选 run 不符合条件，例如含有 nested descriptionList，则不挂载，children 原样保留。

## 六、扁平条件与嵌套失效规则

这项机制只接受扁平 description list。

扁平的定义是：候选 descriptionList run 中任何 descriptionList 节点的内部，不存在 descendant `descriptionList`。

只要候选 run 中任何地方出现嵌套 descriptionList，整个 run 失效，不进行任何 metadata 挂载。

例如：

```adoc
== 标题

fruits:: 2个
pear::: 3个
```

当前 AST 中，`pear::: 3个` 会成为 `fruits` 的 description children 里的 nested descriptionList。因此整个候选 run 失效。不能只挂载 `fruits=2个`，也不能挂载 `pear=3个`。这个 section 不产生 `descriptionMetadata`，原 descriptionList 保留在 children 中。

这个规则的理由是：一旦出现嵌套，description list 已经不再是简单 key/value 表，而是有层级结构的内容。把它压扁成标题 metadata 会丢失结构语义。因此最保守、最清晰的策略是整体失效。

嵌套检查应该递归进行。不要只检查直接 children。只要候选 run 的任意 descendant 中存在 `kind === "descriptionList"`，就判定为嵌套。

## 七、key/value 映射规则

成功候选中的每个 `DescriptionListItemNode` 生成一个或多个 metadata entry。

### 1. key 来源

key 来自 `DescriptionTermNode.text`。

例如：

```adoc
host:: 127.0.0.1
```

key 是 `host`。

### 2. value 来源

value 来自 `DescriptionNode.text`。

如果 description 不存在或 text 不存在，则 value 使用空字符串 `""`。不使用 `undefined`，不使用 `null`，因为 metadata field 的消费面应保持字符串一致性。

### 3. 多行字符串原样保留

如果源文件写：

```adoc
host::
127.0.0.1
苹果
```

则 value 是真实多行字符串：

```ts
"127.0.0.1\n苹果"
```

这里 `\n` 是代码表示真实换行。实现层不需要也不应该把真实换行改成两个字符 `\` 和 `n`。

### 4. 不做 escape/unescape

如果作者真的在源文件里写：

```adoc
description:: 第一行\n第二行
```

那么 value 应保留字面 `\n`，也就是两个字符。实现不把它反解成真实换行。

如果作者写真实多行，就得到真实换行；如果作者写字面 `\n`，就得到字面 `\n`。解析器不自作主张转换。

### 5. 不解析业务类型

所有 value 都是 string。即使写 `5.99`、`true`、`300g`，也不转 number/boolean。这个机制只是标题 metadata 的字符串挂载，不是业务数据解释器。

### 6. 多 term 同 description

AsciiDoc description list 支持多个 term 共享一个 description。例如：

```adoc
Hard drive::
Hard disk::
Persistent storage.
```

官方 AST 会认为这是一个 item，两个 terms 共享一个 description。metadata 映射时应生成两个 entry：

```ts
{
  "Hard drive": "Persistent storage.",
  "Hard disk": "Persistent storage.",
}
```

### 7. 重复 key

如果同一个候选 run 中出现重复 key，建议 `fields` map 采用后写覆盖前写，同时 `entries` 保留完整顺序。这样既让普通消费者容易读取最终字段，也保留审计和诊断能力。

## 八、建议的数据模型

建议在 `SectionNode` 上新增字段：

```ts
descriptionMetadata?: HeadingDescriptionMetadataNode;
```

新增类型可以是：

```ts
type HeadingDescriptionMetadataNode = NodeBase & {
  kind: "headingDescriptionMetadata";
  fields: Record<string, string>;
  entries: HeadingDescriptionMetadataEntry[];
  source?: SourceLayer;
};

type HeadingDescriptionMetadataEntry = {
  key: string;
  value: string;
  term: DescriptionTermNode;
  description?: DescriptionNode;
};
```

`fields` 是给消费者直接使用的 key/value map。

`entries` 保留每个字段来自哪个 term/description 节点，方便 source evidence、重复 key 审计、后续诊断。

`source` 覆盖整个被吸收的 descriptionList run。由于当前 `DescriptionNode.sourceSpan` 对多行 description 的覆盖可能只定位到起始行，list-level source 更适合作为整体证据。单个 entry 仍保留原 term/description 节点供进一步检查。

不要把这个机制塞进 `SectionNode.metadata`。当前 `metadata` 表示标题前 source metadata surface，例如 attrlist/id/title/anchor。标题下 description list 是另一种 source surface。两者应在模型中分开保存，在下游字段投影时再合流。

## 九、对 pretty tree、JSON、RDF 的期望

### 1. JSON

JSON 输出应包含 section 的 `descriptionMetadata` 字段。成功吸收后，原候选 descriptionList 不应继续出现在 `children` 中。

### 2. pretty tree

pretty tree 应把 `descriptionMetadata` 放在 section 内比较靠前的位置，建议在 `metadata` 之后、`children` 之前。多行 value 应沿用当前 serializer 对 multiline string 的展示方式，而不是挤成一行。

理想效果类似：

```text
<section title="大苹果">
    metadata[]
    <headingDescriptionMetadata>
        fields
            描述:
                这是一个极大且红润的苹果。
                它的表面带有清晨的露水。
            颜色: "红色"
    children[]
        <paragraph ...>
```

### 3. RDF 1.2 projection

当前 RDF `attributes.ts` 已经会把标题前 attrlist metadata 投影成 heading direct field predicates。新增 `descriptionMetadata.fields` 后，建议同样投影到 heading direct fields。

例如：

```adoc
== 大苹果

颜色:: 红色
描述::
第一行
第二行
```

RDF heading 上应有：

```turtle
aat:颜色 "红色" .
aat:描述 "第一行\n第二行" .
```

这里 Turtle serializer 会负责合法转义。业务层看到的是同一个字符串值。

嵌套失败时，不应产生这些 RDF direct fields。

## 十、指定样例的正式预期

### `描述列表2.adoc`

第一节：

```adoc
== 你好

host::
127.0.0.1
苹果
banana:: 5个
```

当前 AST 显示 `host` 的 description text 是 `127.0.0.1\n苹果`，`banana` 的 description text 是 `5个`。该 descriptionList 是 `== 你好` 的第一个 direct child，且没有 nested descriptionList，因此应成功挂载：

```ts
descriptionMetadata.fields = {
  host: "127.0.0.1\n苹果",
  banana: "5个",
}
```

成功后，这个 descriptionList 应从 `你好.children` 中移除。后面的普通正文 paragraph 继续保留。

第二节：

```adoc
== 你也好呀

fruits:: 2个
pear::: 3个
```

当前 AST 显示 `pear::: 3个` 是 nested descriptionList。候选 run 存在嵌套，因此整体失效。`你也好呀` 不产生 `descriptionMetadata`，原 descriptionList 保留在 children 中。

### `描述列表3.adoc`

这是标题前 attrlist metadata 样例，不是新 description list metadata 样例。现有机制应继续工作，不应被本次修改破坏。

它说明：官方 attrlist 可以通过一行内 `\n` 或变量 continuation 间接表达多行语义，但写法绕。新 description list 机制提供的是更自然的写法，不是复刻 attrlist 的限制。

## 十一、测试验收标准

至少需要覆盖以下测试：

1. 标题下第一个 direct child 是扁平 descriptionList 时，生成 `descriptionMetadata.fields`。
2. 成功挂载后，被吸收的 descriptionList 从 section.children 移除。
3. 多行 description 保留真实换行。
4. 源里字面 `\n` 保持字面，不反解。
5. 标题和 descriptionList 之间多个空行不影响挂载。
6. 第一个 child 是 paragraph 时，不挂载后续 descriptionList。
7. `[descriptionList, paragraph, descriptionList]` 只处理第一个候选，后续不参与。
8. `[descriptionList, descriptionList, paragraph]` 两个连续 descriptionList 同属候选 run。
9. 候选 run 中任意 nested descriptionList 导致整体失效。
10. 子标题下的 descriptionList 只挂到子标题，不挂到父标题。
11. 多 term 共享 description 时，每个 term 都生成 entry。
12. 重复 key 时，fields 后写覆盖，entries 保留顺序。
13. JSON 和 pretty tree 输出包含 `descriptionMetadata`。
14. RDF direct field projection 包含成功挂载的 descriptionMetadata fields。
15. 嵌套失败时 RDF 不产生这些 fields。
16. 现有标题前 attrlist metadata 测试继续通过。
17. 现有 descriptionList parsing 测试继续通过。

## 十二、实现建议

新增一个纯 AST transform 文件，例如：

```text
src/heading-description-metadata.ts
```

它接收 `AbundantNode[]`，递归处理 section：

1. 找到每个 section 的 direct children。
2. 从 children 起点收集连续 descriptionList run。
3. 如果 run 为空，递归处理子 section 后返回。
4. 如果 run 中存在 nested descriptionList，保留 children，只递归处理子 section。
5. 如果 run 扁平，把 run 转成 `HeadingDescriptionMetadataNode`。
6. 从 section.children 中移除 run。
7. 继续递归处理剩余 children 中的子 section。

接入点建议在 `parseAsciidoctorDocument()` 中，`projectOfficialDocument()` 之后、返回 `AbundantDocument` 之前。这样不需要修改 Asciidoctor adapter、official walker、source interval resolver，也不影响 descriptionList 原始解析能力。

RDF 修改集中在 `src/rdf12-projection/attributes.ts`：保留现有 attrlist metadata 投影，同时读取 `section.descriptionMetadata?.fields` 并投影成 direct field triples。

serializer 修改集中在 `src/serializers.ts`：把 `descriptionMetadata` 加入 child key priority，使 pretty tree 更符合阅读顺序。

## 十三、最终一句话定义

标题描述列表元数据挂载机制，是 `asciidoc-abundant-tree` 在 AST 层对标题 direct children 起点处第一个连续、扁平 description list run 的语义提升：它把 description list 的 term/description 映射为该标题的结构化 metadata fields，使作者能够用自然的 description list 写法声明单行或真实多行标题元数据；若候选列表包含任何嵌套 description list，则整体不挂载并保留为普通内容。

这就是我们要实现的完整机制。
